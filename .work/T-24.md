## Deviations and notes for downstream tasks

- **Local type redefinition, not an `@shelter/engine` runtime dependency.** `Material`, `Glazing`,
  `Layer`/`NamedConstruction` and `EngineError` are all defined locally inside
  `packages/data/src/*.ts`, field-for-field identical to `packages/engine/src/types.ts` (same names,
  same optionality), rather than imported. Reasoning: (a) LOG.md 7.13 lists `@shelter/data`'s runtime
  dependency set as ZERO, same line as the engine; a devDependency-only relationship keeps that true
  in the strongest sense -- the package has no dependency on the engine's *code*, only its *test
  suite* borrows one function from it; (b) this mirrors the documented Area E boundary elsewhere in
  the project ("the data layer does not import physics correlations") -- `packages/data` should be
  loadable, typecheckable and testable (materials/glazing/constructions themselves, tests 1-9, 11-12,
  14) with the engine entirely absent; only test 10 needs real physics, because it is explicitly a
  physics assertion (two constructions share a steady-state U-value); (c) TypeScript's structural
  typing means an object built against the local `Material` type is assignable anywhere the engine's
  `Material` is expected, so nothing downstream loses type safety by this choice. The alternative
  (import the real types) was equally defensible and would have removed the small duplication risk if
  `packages/engine/src/types.ts` ever changes shape; documenting the choice here is the mitigation for
  that risk, per global rule 13.
- **`@shelter/engine` devDependency exists solely for `catalog.test.ts` test 10.** No file under
  `packages/data/src/` imports `@shelter/engine`, checked by `git grep -n "@shelter/engine"
  packages/data/src` (zero hits). `packages/data/package.json` declares it as a `devDependency` only,
  version `"0.1.0"` (npm workspaces, not `workspace:*` -- that is a pnpm-only protocol; D-2 already
  established this repo is npm workspaces). `npm install` linked it via the existing workspace
  symlink mechanism (`node_modules/@shelter/engine -> ../../packages/engine`), no new package-lock
  entries beyond that.
- **`npm run typecheck` was not changed.** T-24's own "Files you may touch" line permits editing only
  `packages/data/**`, `packages/data/package.json`, `packages/data/tsconfig.json`, and the
  `workspaces` array in the root `package.json` -- not the root `scripts.typecheck` line. Per global
  rule 3 ("never touch a file outside your task's allow-list"), the shared root script stays
  `tsc -b packages/engine` and therefore does not build/check `packages/data` at all. Verified
  `packages/data` separately with `npx tsc -b packages/data` (exit 0, see test 13 above). **Finding
  for whoever next legitimately owns root `package.json`:** either add a `tsc -b packages/data`
  invocation to the `typecheck` script, or (cleaner) add a root-level composite `tsconfig.json` with
  `references` to both packages so a single `tsc -b` covers the whole repo; T-24 cannot make that call
  because it is outside this task's file boundary.
- **`GLAZING` has 6 entries, but the 6th is not an independent product line.** LOG.md 7.11's glazing
  table lists 5 genuine U/SHGC/b0 rows (single, double air-filled, double argon+low-E, triple,
  polycarbonate twin-wall) plus a 6th row that is a *formula* ("+ night shutter:
  `1/(1/U + R_sh)`, SHGC unchanged, `R_sh` is a `WindowSpec.shutterResistance` value, not a
  glazing-catalogue property"). Rather than either shipping only 5 `GLAZING` rows (contradicting the
  PROMPT's explicit "All 6") or inventing a 6th product with made-up numbers, `singleGlazingNightShutter`
  was added as a precomputed convenience row using the *already-derived* headline anchor from LOG.md
  7.10 (`U_eff = 1/(1/5.80 + 0.4) = 1.7469879518072289`, matching the documented `1.75 +/- 0.01`
  anchor with margin to spare) with SHGC/tauVis/b0 copied unchanged from `singleGlazing` per the
  table's own note. This is honest (no fabricated number, it is a formula already in the ledger) and
  satisfies "All 6" literally; documented here so nobody mistakes it for an independently-sourced
  product.
- **`tauVis` has no source-document value anywhere in LOG.md 7.11.** The table gives only U, SHGC, b0.
  Filled from generic ASHRAE Handbook of Fundamentals Ch. 15 (Fenestration) / NFRC-typical ranges per
  glazing class, flagged in each `GLAZING` row's own `source` string (`TAU_VIS_NOTE`) so nobody mistakes
  it for a project-specific measured value. Anyone wiring a real product datasheet in later (T-28 or a
  UI catalogue-editing feature) should treat `tauVis` as the softest number in this file.
- **Material.alphaSolar/emissivity are informational, not physics-critical, today.** Confirmed by
  `git grep -n "\.alphaSolar\|\.emissivity" packages/engine/src` excluding `types.ts`: zero hits. The
  engine's actual solar/longwave code reads `Surface.exteriorAbsorptivity` / `exteriorEmissivity` /
  `interiorEmissivity`, which are independent fields a caller (a preset, T-28) sets directly -- they
  are not derived automatically from a construction's outermost material. This means the placeholder
  alphaSolar/emissivity values assigned to insulation materials (and to the two structural materials
  with no matching finish-table row, stone masonry and timber) cannot silently bias a simulation
  today; they only affect a future UI card or a future T-28 preset-authoring convenience that chooses
  to read them. Flagged here so T-28 knows these are catalogue defaults, not measured data, for the
  handful of rows called out in their own `source` strings.
- **8 surface finishes, applied two ways.** 3 of the 8 (dark mud/earth, red brick, grey concrete) are
  applied as `alphaSolar`/`emissivity` directly onto existing structural rows that are physically that
  finish already exposed (mud brick/rammed earth/compressed earth block/mud plaster; fired clay brick;
  dense concrete/RCC/cement plaster). The other 5 (black paint, white paint, whitewash/lime,
  galvanised steel bright, galvanised steel weathered) are shipped as standalone `category: 'finish'`
  material rows (`blackPaint`, `whitePaint`, `whitewashLime`, `cgiBright`, plus `steelCGI` itself
  carrying the weathered-galvanised values as its default condition) because they represent an
  applied coat/condition a user genuinely chooses independently of the substrate underneath, not a
  property of one specific bulk material.
- **27 materials total, not 23.** The PROMPT's base tables sum to 23 rows (11 structural/mass + 8
  insulation + 4 other). The 5 standalone finish rows above bring the total to 27. This is additive,
  not a substitution -- every one of the base 23 rows is present with its exact §7.11 values (verified
  by test 4/5/6 spot checks), and `category: 'finish'` needed at least one real row to satisfy
  acceptance test 7, so the extra rows are load-bearing, not padding.
- No preset (T-28) or weather (T-25/T-27) content was added, per the PROMPT's explicit exclusions.
