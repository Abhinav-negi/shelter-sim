## Deviations and notes for downstream tasks

- No deviations from the PROMPT. Both functions are pure, side-effect-free, and use
  only the approved `EngineError`/`Kelvin` imports from `types.ts`/`units.ts` (import
  only -- neither file was modified).
- `pcmEnthalpy` is deliberately closed-form (a piecewise-linear antiderivative), not a
  numerical quadrature, per the PROMPT.
- For **T-20** (StorageElement / wiring PCM into the solver) and whoever eventually
  wires a PCM node into `solve/integrator.ts` / `solve/assemble.ts`:
  - Use `apparentHeatCapacity(cBase, latentHeat, meltPoint, meltRangeK, T_node)` to get
    the node's instantaneous capacitance per unit mass; multiply by mass for `C_j`.
  - For the energy-balance residual's `ΔStored` term (LOG.md 7.4), do NOT do
    `C_j(T_end) * (T_end - T_0)`. Instead use `pcmEnthalpy(t_end) - pcmEnthalpy(t_0)`
    (times mass) at each step and sum across steps (trapezoidal by construction, since
    `pcmEnthalpy` is the exact closed-form integral) -- this is what the contract in
    §7.4 requires and is exactly what avoids mis-counting latent heat crossed mid-step.
  - Respect the refresh-cadence contract (T-11): do not refactorise the matrix more
    often because of PCM. Either add a nonlinear (Picard) iteration within a step so the
    apparent capacitance converges, or lag it (evaluate at the previous step's
    temperature) and push a `meta.warnings` entry when it's lagged. If apparent heat
    capacity moves by more than some threshold fraction within one refresh interval,
    warn -- do not silently refactorise more often to compensate.
  - `pcm.ts` is standalone/unwired by design (T-19 scope); it exports no node type and
    touches no shared contract file. T-20 (or whichever task wires it in) will need to
    define how a PCM layer's mass and thickness map onto `cBase`/`latentHeat` inputs
    (likely per unit area, consistent with `envelope/mesh.ts`'s `capacityPerArea`
    convention) -- that mapping is not decided here.
