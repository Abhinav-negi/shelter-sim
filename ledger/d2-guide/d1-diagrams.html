How a shelter design becomes a simulation

What runs in the browser, on the server, in MongoDB and in the thermal engine, and how a request moves between them. Every claim points to a file in apps/studio or apps/studio-server. The API contract is apps/studio-server/API.md.

System

Two new apps sit beside the original ShelterSim, which is frozen. The Studio server imports the engine and data packages read-only. The browser never runs physics: it only imports types.

Client internals

One zustand store holds the ShelterDesign. The controls, the 3D part popover and the preview all read and write that store. Selection state lives in a separate store, so hovering or clicking a part never marks the design dirty or triggers a simulation.

Server internals

index.ts loads the environment and exits if MONGODB_URI or JWT_SECRET is missing. It then calls buildApp() in app.ts, connects Mongo and listens. Every route follows the same path: route → service → Mongoose model. One error handler turns typed errors into stable codes.

Provider seam

SimulationProvider {id, run} in providers/index.ts has one implementation, fast-physics, which wraps the engine's simulate(). Routes call the provider and never call the engine directly. There is no mock provider.

Request sequences

A preview and a saved run use the same pipeline. They differ in the input (the live store vs the stored design) and in what happens to the result.

Custom location weather

Preset sites use typical-year weather bundled in @shelter/data. A custom site fetches real 2023 weather. The fetch is async and assemble() is sync, so design/prepare.ts resolves weather first and passes it in as a closure.

Auth

A session is a JWT stored in an httpOnly cookie. There are no tokens in JavaScript and no refresh endpoint.

  1. Register / login (auth/routes.ts): the password is hashed with scrypt and a 16-byte salt (auth/password.ts) and checked with timingSafeEqual. A login with an unknown email still hashes against a dummy hash, so response timing can't reveal which accounts exist.
  2. Cookie: the server signs {sub: userId} with JWT_SECRET and sets it as the cookie token. It lasts 7 days and is httpOnly and sameSite=lax. It is secure only when NODE_ENV=production.
  3. Guard: auth/authenticate.ts runs as a preHandler on every designs and simulations route and on /auth/me. A bad or missing cookie returns 401. A resource you don't own returns 404, so its existence isn't revealed.
  4. Client: RequireAuth calls /auth/me. On 401 or a network error it redirects to /login. Logout clears the cookie.

Designs saved before v2 have no shape or storeys. They open as a one-storey box: store.ts loadDesign fills in the defaults, and so does viewer/geometry.ts.

ShelterDesign → surfaces

design/assemble.ts turns a design into the engine's SimulationRequest. The engine only understands flat surfaces with an area, tilt and azimuth. Cylinders and domes are therefore approximated as flat facets, and the engine itself was not changed.

  1. Load the base request from the preset (resolvePreset).
  2. Set weather and site from design.location: bundled TMY for a preset site, weatherFor() for a custom one (422 if it's missing).
  3. Set building.azimuth = azimuthDeg. The engine applies the rotation.
  4. Build the shape: setSize (box), cylinderGeometry or domeGeometry, then addIntermediateSlab if there are 2 storeys.
  5. Apply wall, roof and floor construction overrides, only where they aren't null.
  6. Set the window-to-wall ratio per quadrant. A wall belongs to the quadrant within ±45° of its facing; ties go to S or N.
  7. Apply the glazing type and night shutters (R 0.4, 20:00–06:00).
  8. Apply the occupancy preset (OCCUPANCY_PRESETS).
  9. Set the options: 1 simulated day and skyModel: 'isotropic'. This setting is load-bearing; the other sky model diverges on these presets.

A one-storey box must produce a request identical to the frozen app's for the same input. test/parity.test.ts checks this by comparing canonical request hashes against apps/server/src/assemble.ts.
