`useAnimatedHour`, `useInView`, `useForceDarkTokens`), `sampleAtHour.ts` (+`.test.ts`), `Hero.tsx`, `ShapeStrip.tsx`,

**Condition 1 (dark hero, autoRotate, sun animation, temp strip) — the interesting design decision.**
"Dark tokens regardless of theme" has to reach the *embedded* `ShelterViewer`'s own colours, which come from
`useThemeColors()` — a hook that reads `getComputedStyle(document.documentElement)` (always the real `<html>`
root, never a caller's subtree), and that file is not on this task's May-touch list. A scoped CSS override on a
wrapper div therefore cannot reach it: custom properties only cascade to descendants, and that call is hardcoded
to the root itself. Resolution used: `useForceDarkTokens(heroRef)` toggles the *same* `data-theme` attribute
`lib/theme.ts`'s own toggle already drives on `<html>` — set to `'dark'` for as long as an `IntersectionObserver`
says the hero is anywhere in the viewport, restored to whatever it was the instant it isn't. Reusing the real
attribute (rather than poking `--paper` etc. via inline style directly, which was the first attempt) mattered for
correctness, not just economy: `useThemeColors` has its own `MutationObserver` watching exactly `data-theme` on
`document.documentElement`, so every mounted `ShelterViewer` re-reads colours and re-renders when it flips. The
first (inline-style) version changed the cascade but told nothing already-rendered to look again, which left any
`frameloop="demand"` canvas that happened to mount *during* the hero's dark-forced window (e.g. a shape-strip card
scrolled into view right at the hero/strip boundary) frozen on stale (dark) colours forever after — caught by eye
in a scripted, scroll-stepped screenshot, not from a single before/after pair. Because header/`AppShell` is not
sticky, this only visibly darkens the header while the hero itself is in view, which reads as intentional
("cinematic dark hero absorbing the nav"), not as a bug; everything below the hero (shape strip, stages, chart,
closing CTA) genuinely still follows the real light/dark toggle once scrolled past it — confirmed in the
light/dark scrolled-through screenshots below, which differ from each other exactly where they should.

`autoRotate` (ShelterViewer.tsx, the one allowed change): optional, default `false`. Passed straight to drei's
`OrbitControls`; a `RotatePump` (`useFrame(({invalidate}) => invalidate())`) is mounted only while the prop is on,
so `frameloop="demand"` keeps rendering during continuous auto-rotation without touching behaviour for any other
caller (Studio, DevViewer, the shape-strip's own static instances, which never pass the prop). Landing gates it
(and the sun sweep) on `!reducedMotion`.

The sun sweep (`useAnimatedHour`, hooks.ts) is a plain `requestAnimationFrame` triangle wave, dawn (6) -> dusk
(18) -> dawn, 90 s per full cycle ("slow and purposeful", not a spinner); fixed at 6 (the original F4 hero's own
static hour) when reduced motion or not yet active.

The temperature strip samples the *same* real preview Landing already fetches once (`usePreview`, lifted out of
the old per-stage `LivePreviewChart`) at the live animated hour via `sampleAtHour.ts` (linear interpolation between
the two bracketing 24 h samples — smooth, matching the sun's own continuous motion, not a discrete jump every
model timestep). Omitted entirely if the preview call fails or hasn't resolved yet — never fake data, same rule
F4/Q1F already established.

**Condition 2 (sections).** (a) `ShapeStrip.tsx`: 3 cards, each its own `useInView` — the (already-lazy)
`ShelterViewer` element is only rendered once its card is scrolled into view, so 3 idle WebGL contexts never sit
on the page at load; `{...options.defaults, shape}` per the already-merged G3/G2 contract, fixed noon hour, no
auto-rotate (not asked for, and unrequested motion is exactly what the "purposeful, not decorative" motion rule
warns against). (b) `Stages.tsx`: same 4 stages, each `<li>` gets `.reveal` + `is-visible` from its own
`useInView(0.2)`, once true and never re-hidden (re-hiding on scroll-up would read as distracting, not
purposeful). (c) `Chart.tsx`: the live chart is now its own section (previously folded into the "Fast physics"
stage's body, F4) — same shared preview, never a second call. (d) A closing CTA section, inline in `Landing.tsx`
(small enough not to warrant its own file).

**Condition 3 (reduced motion).** Two independent layers, deliberately redundant: (1) JS — `useReducedMotion`
(hooks.ts) gates `autoRotate` and the hour sweep at the React level, so under reduced motion the hero's hour is
pinned to 6 and `autoRotate` is never passed as `true`. (2) CSS — `.reveal`'s own
`@media (prefers-reduced-motion: reduce)` block forces `opacity:1; transform:none; transition:none` unconditionally,
so stage content is visible even if `useInView`'s `IntersectionObserver` never fires for some reason (belt and
suspenders, not just the JS gate). Verified with Playwright's `reducedMotion:'reduce'` context option: hero hour
reads "At 06:00" (unanimated), all 4 stages render immediately without scrolling, building still clearly visible —
`landing-1440-reduced-{hero,scrolled-full}.png`.

**Condition 4 (banned list).** No gradient blobs (the sky is the pre-existing physical WebGL fog, unchanged), no
glassmorphism, no pill badges (CTAs are the pre-existing `rounded-sm` buttons, just bigger), no fake stats / logos
/ testimonials, no stock imagery. The shape strip is a functional 3-up display of 3 real, distinct, live-simulated
geometries (not an icon+blurb "feature" triplet), which is condition 2(a)'s own explicit ask, not the banned
"generic 3-column feature grid".

already merged, before any G5 change): eager `index-*.js` = **306.72 kB**. After G5: **310.84 kB** (+4.1 kB) —
