# P2 — Auth, designs, simulations (Mongo)
Status: DONE      Depends on: P1

## Goal
Users can register, log in and log out, and own designs and simulation history. Each simulation freezes its input
snapshot.

## Read
`ledger/PLAN.md` (§Server) · `apps/studio-server/API.md` · `apps/studio-server/src/{app.ts,env.ts,design/types.ts,providers/*}`

## May touch / must not touch
May: `apps/studio-server/src/{db.ts,auth/**,designs/**,simulations/**,app.ts}`, `test/**`, `API.md`.
Must not: anything outside `apps/studio-server`. **No npm install** (P1 pre-installed everything).

## Conditions
1. `POST /api/auth/register|login|logout`, `GET /api/auth/me`. The password is hashed with `crypto.scrypt` and a
   random salt, and is never returned. The JWT is in an httpOnly, SameSite=Lax cookie (Secure when
   NODE_ENV=production). Duplicate email → 409 `EMAIL_TAKEN`. Bad login → 401 `INVALID_CREDENTIALS` (same message for
   an unknown email).
2. Designs CRUD (`/api/designs`, `/:id`). The `design` body is validated with P1's ShelterDesign schema. List is newest
   first. Another user's id → 404.
3. `POST /api/designs/:id/simulations` runs through the provider and stores `{provider, engineVersion, requestHash,
   inputSnapshot, kpis, result}`. Editing the design afterwards leaves the stored snapshot and result unchanged
   (test it).
4. `GET /api/designs/:id/simulations` lists newest first **without** `result`. `GET /api/simulations/:id` returns it
   in full.
5. Startup fails with a clear message if `MONGODB_URI` or `JWT_SECRET` is missing (except in tests).
6. Tests use `mongodb-memory-server` and cover every condition above, including cross-user isolation.
   `npm test -w @shelter/studio-server` and tsc are clean.

## Rules
Routes → service functions → Mongoose models. No DB calls inside route handlers. Keep `inputSnapshot` a deep copy.

## Evidence

**Layout added:** `src/db.ts` (mongoose connect/disconnect, wraps the default connection — P3 uses
the same one for `weatherCache`); `src/auth/{model,password,service,authenticate,routes}.ts`;
`src/designs/{model,service,routes}.ts`; `src/simulations/{model,service,routes}.ts`;
`test/{mongo.test.ts,index-startup.test.ts}`. `app.ts` gained: `@fastify/cookie`/`@fastify/jwt`
registration, registration of the three route plugins, `BuildAppOptions` (`jwtSecret?`, `nodeEnv?`)
on `buildApp()`, `export` on the existing `shelterDesignSchema()` (reused by designs/routes.ts —
see gotchas), and three new `instanceof` branches in the central error handler
(`EmailTakenError`→409, `InvalidCredentialsError`→401, `NotFoundError`→404). `index.ts` now refuses
to start without both `MONGODB_URI` and `JWT_SECRET` (condition 5), then calls `connectDb()` before
`listen()`.

**Decisions + why:**
- **Routes → service → model**, one folder per resource, mirroring the collections in PLAN.md
  §Server. No DB calls in route handlers anywhere — every handler is `await someServiceFn(...)`.
- **Auth cookie via `@fastify/jwt`'s built-in `cookie` option** (`cookie: {cookieName: 'token',
  signed: false}`, registered after `@fastify/cookie`), not hand-rolled cookie parsing —
  `request.jwtVerify()` reads the JWT straight out of the `token` cookie. `src/auth/authenticate.ts`
  wraps that in one `authenticate` preHandler (401 `UNAUTHENTICATED` on failure) + a `userId()`
  helper reading `request.user.sub`, imported by all three protected route plugins.
- **`buildApp(opts?: {jwtSecret?, nodeEnv?})`**: `jwtSecret` defaults to an insecure dev string
  (fine — nothing in `buildApp()` touches a DB either, matching P1's original "no DB required"
  design; every test in this package calls `buildApp()` directly). `nodeEnv` defaults to
  `process.env.NODE_ENV` and only flips the auth cookie's `Secure` flag. The REAL fail-fast lives in
  `index.ts`, which requires `MONGODB_URI`+`JWT_SECRET` before ever calling `buildApp()` or
  `connectDb()` — this is what condition 5's "(except in tests)" is pointing at.
- **`shelterDesignSchema()` exported from `app.ts`, imported by `designs/routes.ts`** so the
  `design` field of `POST/PUT /api/designs` is validated with the *exact* ShelterDesign ajv schema
  `/api/simulate/preview` uses (condition 2 says "P1's ShelterDesign schema", not a second copy).
  This makes `app.ts`↔`designs/routes.ts` a static ESM import cycle; made safe by only calling
  `shelterDesignSchema()` inside the plugin's async function body (registration time, after both
  modules are fully evaluated), never at either module's top level — see gotchas.
- **One error class per failure mode**, following P1's `CustomLocationUnavailableError` precedent
  exactly: `EmailTakenError`/`InvalidCredentialsError` (auth/service.ts), `NotFoundError`
  (designs/service.ts, reused by simulations/service.ts — a design 404 and a simulation 404 are the
  same shape). Central `setErrorHandler` in `app.ts` does the `instanceof` → status mapping, same
  pattern as the engine/CustomLocationUnavailable branches already there. No shared `AppError` base
  class — three tiny classes is less machinery than one generic one for three call sites.
- **`inputSnapshot` freezing (condition 3):** `runSimulation` (`simulations/service.ts`) does
  `structuredClone(designDoc.design)` before calling `assemble()`, and stores that clone, not a
  reference to the live mongoose document's `design` field. Verified by test (design PUT'd after the
  run; stored snapshot/kpis/result asserted unchanged).
- **`engineVersion`:** read from `packages/engine/package.json` at module load
  (`simulations/service.ts`'s `readEngineVersion()`), copying the exact pattern already used by
  `apps/web/lib/repo/runs.ts`'s `ENGINE_VERSION` (found by grep, that file is frozen/unrelated but a
  good precedent) — never hardcoded, so a version bump doesn't need a code change here.
- **Ownership checks are 404, never 403** (condition 2/4): `designs/service.ts`'s
  `getOwnedDesignDoc(ownerId, id)` does `Design.findOne({_id: id, ownerId})` and throws
  `NotFoundError` if nothing matches — a wrong-owner id and a nonexistent id are indistinguishable
  by design (don't leak existence). `simulations/service.ts` reuses this for the design-scoped
  routes, then does its own owner-scoped `findOne` for `GET /api/simulations/:id`.
- **List ordering:** `Design.find({ownerId}).sort({updatedAt: -1})` and
  `Simulation.find({designId}).sort({createdAt: -1})` — both match PLAN.md §Server's stated indexes
  (`{ownerId,updatedAt:-1}` / `{designId,createdAt:-1}`), which the schemas also declare via
  `.index(...)` so real Mongo actually uses them.
- **`models['X'] ?? model('X', schema)` guard** in all three model files — avoids
  `OverwriteModelError` if a module is evaluated more than once against the same mongoose default
  connection (e.g. across test files in one vitest process).

**Gotchas:**
- **`mongoose`'s named export `models` doesn't exist at runtime** (only in the type declarations) —
  Node's ESM/CJS interop (`cjs-module-lexer`) can't statically see it because mongoose sets it via a
  dynamic property, not a literal assignment, on `module.exports`. `import { models } from
  'mongoose'` type-checks fine under `tsc` but throws `SyntaxError: The requested module 'mongoose'
  does not provide an export named 'models'` at actual runtime (`tsx`/Node's real ESM loader) — tsc
  alone would NOT have caught this. Fix, in all three model files: `import mongoose, { Schema, ... }
  from 'mongoose'; const { model, models } = mongoose;` (destructure off the default export at
  runtime instead of naming it as an ESM import). Caught by actually running the app (a scratch
  `app.inject` script), not by `tsc -p ... --noEmit` — worth remembering: this package's `tsc` check
  does NOT catch every mongoose ESM-interop mismatch, so a real run is part of "done" here, not
  optional polish.
- **`getOwnedDesignDoc`'s return type must be `HydratedDocument<DesignDoc>`, not plain `DesignDoc`**
  — the first draft annotated it as `Promise<DesignDoc>` (the plain interface), and `updateDesign`'s
  `doc.save()` / `deleteDesign`'s `doc.deleteOne()` then failed `tsc` (`TS2339`) because the plain
  interface has no Mongoose Document methods. `HydratedDocument<DesignDoc>` from `mongoose` fixes it;
  `toSummary()` still accepts it (structurally a superset of `DesignDoc`).
- **The `app.ts` ↔ `designs/routes.ts` import cycle is safe but deliberate** — `shelterDesignSchema`
  is a real `function` declaration (hoisted/initialized during ESM instantiation, not evaluation),
  and `designBodySchema` in `designs/routes.ts` is built inside the plugin's async function body
  (called only once `buildApp()` runs, well after module graph evaluation finishes), never at either
  module's top level. Flagging this because a future refactor that moves `designBodySchema` to
  module-top-level `const` would very likely break at runtime in a way `tsc` won't catch either
  (same class of issue as the `mongoose` one above) — actually running the test suite is what caught
  it working, not a type check.
- **`mongodb-memory-server` needs to download a ~82 MB `mongod` binary on first use** — no cached
  binary existed in this environment; confirmed network access to `fastdl.mongodb.org` works and did
  a standalone download-and-boot probe (~23 s) before writing tests, so the real test run wouldn't
  silently hang/timeout on a cold cache. Binary is now cached at `~/.cache/mongodb-binaries/`, so the
  34-test suite runs in ~5 s end-to-end.
- Ran `npm ci` fresh in this worktree per the brief (not `npm install`) — `package-lock.json` is
  untouched (`git diff --stat studio/main -- ... package-lock.json` empty).
