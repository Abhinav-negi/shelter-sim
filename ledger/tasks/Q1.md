**"Viewer bounding box grows" — how it's actually measured and why.** Screenshotting just the `<canvas>` and diffing
against a single reference colour (the corner pixel) turned out to be broken: `ShelterViewer`'s background is not
flat — `<fog>` + the ground plane produce a continuous soft gradient across the *entire* canvas (confirmed by
dumping a real canvas screenshot and looking at it), so a single-colour diff saturates to "the whole canvas differs"
regardless of the building's actual size. `apps/studio/e2e/png.mjs`'s `edgeBBox()` uses local gradient magnitude
(Sobel-ish finite difference) instead, which isolates real geometry (building faces/edges, the compass, the sun
dash) from that smooth backdrop. Verified against the same two real screenshots: the flat-colour approach reported
an *identical* full-canvas bbox before/after (false negative); the edge-detection approach reported 122,508 px²
before → 157,920 px² after (+29%), matching what the screenshots show by eye.

Second subtlety: F2c's camera auto-frames to `cameraFootprint = max(lengthM, widthM)` specifically so the compass/
building never crop regardless of the design's size — which means naively varying Width alone (especially past
Length) can leave the on-screen extent roughly constant, since the camera pulls back to compensate exactly (that's
F2c's own intended behaviour, not a bug). The flow script sets **Length = 25 m first**, then varies Width from 3 m
to 20 m (staying below Length the whole time), so `cameraFootprint` never changes and the camera never compensates
— only then does growing Width actually grow the rendered extent, which is what condition 1 is actually asking to
be proven. This is flagged here for whoever next touches camera framing: the naive "just drag the Width slider"
version of this test would have been flaky/misleading against F2c's own correct behaviour.

**Console-error allowlist.** Two categories are excluded from the "0 console errors" count, both pre-existing and
documented by earlier tasks' own Evidence, not this task's discovery: (1) the `THREE.Clock` deprecation warning
(`@react-three/fiber`'s own internal, pinned dependency version, present in every render). (2) `Failed to load
resource: ... 401` specifically for `/api/auth/me` — Chromium logs any non-2xx `fetch()` response to the console
automatically regardless of whether app code handles it (it does, gracefully: `RequireAuth`'s `getMe()` catches it
and renders `<Navigate>`); step 10 deliberately visits `/app` while logged out to prove that exact redirect, so
triggering this exact, well-understood entry is unavoidable short of not testing the guard at all — F4.md's Evidence
documents the identical tradeoff for its own deliberately-provoked 400/401s. The allowlist checks both the message
text *and* the failing resource's URL (`msg.location().url`), so it can't accidentally swallow an unrelated 401.
Zero *other* console errors or `pageerror`s across the whole flow.

`POST /api/simulate/preview` for the error state). Screenshots: `<scratchpad>/q1/screenshots/*.png` (32 files).

**Methodology gotcha worth recording:** an initial pass used `page.screenshot({fullPage: true})` for every capture.
On the Studio route this produced screenshots 1.7-2.3x taller than the real viewport with a large blank tail (e.g.
390×**1936** instead of 390×844). Root cause: Studio's own root is intentionally capped to `h-[calc(100dvh-56px)]`
(F3.md review round 2, so the 3D viewer's aspect ratio stays sane) — but Playwright's `fullPage` capture works by
temporarily resizing the browser to the page's measured `scrollHeight` before shooting, and that resize itself feeds
back into `dvh`, growing the cap and leaving blank space below the real content. This is a capture-methodology
artifact, not a product bug (confirmed by comparing against plain, non-`fullPage` shots, which came out exactly
390×844/1440×900 with no blank tail and pixel-identical visible content). Switched every capture to plain
`page.screenshot()` (matches F3/F4's own precedent — their screenshots were sized exactly 1440×900/390×844) and
re-ran; also matches "viewport composition" as a literal QA criterion better than a full-scroll capture would.
