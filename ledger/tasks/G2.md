# G2 — Shape contract (box / cylinder / dome, storeys) + server facet surfaces

## Goal
`ShelterDesign` can describe a box, a cylinder or a dome, with 1 or 2 storeys. The studio-server turns non-box
shapes into facet surfaces for the (frozen, surface-based) engine. The box path is byte-identical to today.

## Contract
```ts
shape?: 'box' | 'cylinder' | 'dome'   // default 'box' when absent
storeys?: 1 | 2                       // default 1 when absent; heightM = height PER storey; dome ⇒ must be 1
```
Cylinder: `lengthM` = diameter, `widthM` ignored. Dome: hemisphere, `lengthM` = diameter, `widthM`/`heightM` ignored.
Optional so every saved design and every frozen `inputSnapshot` stays valid (missing ⇒ box, 1 storey).

## Conditions

2. Schema in `app.ts` accepts the fields, rejects bad values (`shape:'pyramid'`, `storeys:3`, dome+storeys 2) with the

3. Box, 1 storey, fields absent or explicit: the assembled `SimulationRequest` is deep-equal to today's
   (`parity.test.ts` unchanged and green; add a test that explicit `shape:'box',storeys:1` equals absent).
4. Cylinder: 12 wall facets at azimuth k·30° (−150..180), each area πD·h/12 (h = heightM·storeys); roof and floor
   area πr² each; `volume` πr²h. Facets copy the preset S wall / roof / floor template (construction, boundary,
   absorptivity, emissivities); construction overrides still apply.
5. Dome: 3 elevation bands × 12 sectors, band area 2πr·Δz/12 (spherical zone), tilt = 90° − band mid-elevation;
   tilt ≥ 60° ⇒ `wall` (wall construction, can host windows), else `roof`; floor πr²; volume ⅔πr³.

7. WWR: `wallForOrientation` generalised to the walls within ±45° of the cardinal azimuth (ties at ±45° → S/N); the

8. Tests (pure vitest): area and volume sums per shape equal the closed forms within 1e-9; every generated request
   passes `validate`; `POST /api/simulate/preview` returns 200 with finite KPIs for cylinder, dome, box×2 and

### Design decisions + why

- **Box byte-identity.** `setSize` keeps its exact old body except `heightM` -> a locally computed
  `wallHeightM = size.heightM * storeys` (default param `storeys: Storeys = 1`), used only for wall
  area / volume. Every existing call implicitly used `storeys=1`; the one new call site in `assemble()`
  passes `design.storeys ?? 1`. No other line in `setSize` changed. Verified by the parity test (unchanged,
  green) and a new hash-equality test (`shapes.test.ts`: explicit `shape:'box',storeys:1` === absent).
- **`setSize` vs `setShapeFacets`.** Per V2.md: box always calls `setSize` (never touches `setShapeFacets`);
  cylinder/dome call `setShapeFacets` instead, which pulls S-wall/roof/floor TEMPLATES from the CURRENT
  `request.building.surfaces` (i.e. the preset's own surfaces, read before any construction override --
  `assemble`'s step order already puts size/shape at step 3, overrides at step 4, so this is automatic, not
  a reordering I had to do). `withConstructionForType` (step 4) replaces a surface TYPE's construction for
  ALL surfaces of that type, so it applies uniformly whether there are 4 walls (box) or 12/24 (cylinder/dome)
  with no changes needed there.
- **WWR generalisation (`wallForOrientation` -> `wallsInQuadrant`).** A wall's quadrant is decided by
  `orientationForAzimuth`: S = `[-45,45]`, W = `(45,135)`, N = `azimuth<=-135 || azimuth>=135`, E = else --
  this places the ±45°/±135° ties on S/N per the spec. `setWwr` applies the SAME clamped ratio to each wall's
  OWN area; since every wall in a quadrant gets that ratio, the summed window area is automatically
  proportional to each wall's share of the quadrant's total area -- no separate proportion math needed. For a
  box (1 wall/quadrant) this is exactly the old behaviour.
- **Cylinder/dome clear `windows` before regenerating** (stale `hostSurfaceId` would reference a wall id like
  `wallSouth` that no longer exists once facets are replaced) -- harmless because `assemble()`'s step 5
  unconditionally re-derives every orientation's windows from `design.windowWwr` right after, regardless of
  shape.
- **Materials record + storage elements.** `buildModel` (`packages/engine/src/solve/assemble.ts`) requires
  `materials[storageElement.materialId]` to exist or it throws `UNKNOWN_MATERIAL`. `usedMaterialIds` (this
  file) now also scans `building.storageElements`, and `addIntermediateSlab` calls `finalizeWithCatalogue`
  itself right after adding the slab, so the materials record is correct regardless of whether a later
  `wallConstruction`/`roofConstruction`/`floorConstruction` override runs afterward (which would otherwise
  rebuild the record from a Set that must still include the slab's id).
- **Slab material choice ("the preset floor material").** V2.md's wording is ambiguous between "the design's
  current floor material" and "the original preset's floor material". I resolved it operationally: the slab
  step runs BEFORE any construction override (step 3, before step 4), so it always reads the CURRENT floor
  surface's construction at that point in the pipeline -- which for every real call *is* the preset's own,
  unmodified floor construction. I use the LAST (innermost, room-facing) layer's material, e.g.
  `rammedEarth` for `traditionalLadakhiByre` (its `EARTH_FLOOR` stack is `[gravelSoilFill, rammedEarth]`,
  ext->int) rather than the ground-side fill layer -- this is a judgement call, documented in `API.md` §3c
  and here; no test locks in a *specific* material choice, only that the assembled request is valid and
  simulates.
- **Slab constants (documented, not measured -- ledger rule "no hidden approximations"):**
  `SLAB_THICKNESS_M = 0.15` m (a nominal thin intermediate deck) and
  `SLAB_CONVECTIVE_COEFFICIENT = 8` W/(m^2*K) (nominal interior convective coefficient, doubled in
  `conductanceToRoom` for both faces of the slab since the single-zone approximation puts both in the same
  air node). `massKg = footprint * 0.15 * density`; `surfaceAreaToRoom = 2*footprint`. `validateRequest`
  (`packages/engine/src/validate.ts`) does not check `storageElements` at all (confirmed by reading it), so
  there's no engine-side range constraint on these -- the only real correctness requirement, confirmed by
  reading `packages/engine/src/solve/assemble.ts` / `storage/waterMass.ts`, is that `materials[materialId]`
  exists (see above) and (for `kind:'pcm'` only, not used here) `latentHeat`/`meltPoint` are set.
- **Dome bands.** 3 equal-HEIGHT bands (`dz = r/3`), not equal-angle -- required by the "spherical zone"
  formula in the contract (`2*pi*r*dz/12`, the Archimedes hat-box identity, area depends only on height).
  `tilt = 90 - asin(zMid/r_in_degrees)`. Band mid-elevations for a 3-band split: ~9.59° (tilt 80.4, wall),
  30° exactly (tilt 60, wall -- the `>=60` boundary is inclusive by design, spec says "tilt >= 60"), ~56.44°
  (tilt 33.6, roof). So bands 0,1 (24 facets) are walls, band 2 (12 facets) is the roof cap -- verified by a
  closed-form test.

### Gotchas for a successor

- `orientationForAzimuth` assumes its input is already in `(-180,180]` -- true for every azimuth this file
  ever produces (box: 0/-90/90/180; cylinder/dome: -150..180 step 30) -- so it does NOT do full modulo
  wraparound normalisation. Don't feed it an unnormalised azimuth (e.g. 270) without adding that first.
  `packages/engine/src/solve/assemble.ts` has its own `normaliseAzimuth` for the whole-building rotation
  case, deliberately not reused here (it's engine-internal, and studio-server's per-surface azimuths stay
  relative to south, unrotated, by design).
- `ajv`'s `if`/`then` (used for the dome+storeys-2 rule in `app.ts`'s `shelterDesignSchema()`) DOES work under
  fastify v5's default ajv setup -- confirmed by a passing test (`shape:'dome',storeys:2` -> 400). If a future
  ajv upgrade changes this, the fallback is a plain post-schema check in the route handler that throws a
  VALIDATION_ERROR-shaped error the same way `CustomLocationUnavailableError` does.
- `cylinderGeometry`/`domeGeometry`/`ShapeTemplates` are exported from `design/assemble.ts` purely so tests
  can check closed forms directly against a synthetic `ShapeTemplates` (no real preset needed) -- see
  `test/shapes.test.ts`'s `fakeSurface` helper.

  **Plausibility.** Note `lengthM` is reused literally as the cylinder/dome DIAMETER (per the contract), so
  at the defaults (`lengthM=5`) the cylinder/dome are smaller buildings than the 5x5 m box (floor area
  `pi*2.5^2=19.6 m^2` vs `25 m^2`; cylinder volume 51.1 m^3, dome volume 32.7 m^3, vs the box's 65 m^3) -- NOT
  an apples-to-apples comparison of the same footprint. `familyLivestock`'s internal gains (livestock body
  heat, cooking) are a FIXED absolute wattage regardless of shape/volume, so a smaller enclosed volume traps
  the same heat input into less air+mass and runs warmer: box (65 m^3, coolest) < cylinder (51.1 m^3) < dome
  (32.7 m^3, warmest) tracks inversely with volume, which is the expected direction. The 2-storey cases are
  colder than their 1-storey counterparts because wall area AND volume double while the same fixed gains and
  a proportionally-scaled (WWR-ratio-preserved, so also doubled) window area now have twice the envelope to
  lose heat through and twice the air to heat -- also the expected direction for stacking an unheated second
  storey onto a single zone. I did NOT verify these against a same-footprint cylinder (that comparison is the
  separate `shapes.test.ts` "less wall area" test, done algebraically instead, since it isolates envelope
  shape from volume/gains effects cleanly).
