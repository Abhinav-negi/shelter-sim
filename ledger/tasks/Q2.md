### Condition 1 — `flow.mjs` extended

**Pre-existing regression found and fixed first.** Before adding anything, ran the unmodified `flow.mjs` to
baseline it: it **failed** — G1 (merged since Q1 wrote this script) added a typed `NumberInput` next to every
slider sharing the same accessible label (`aria-label={label}` on the `NumberInput`, no explicit label on the
`<input type=range>` — its name comes from `FieldRow`'s `<label htmlFor=...>`). `getByLabel('Length'/'Width')` is
therefore ambiguous (`role=slider` and `role=spinbutton` both named "Length") and `locator.evaluate` threw a
strict-mode violation. Fixed by switching the three call sites to `getByRole('slider', {name})` — the exact same
gotcha G4.md's own verification script hit and fixed the same way. Re-verified all 13 original Q1 checks pass
before adding any Q2 step (committed separately, `272a97c`, so this fix is visible independent of the new steps).

**New steps added**, all on the flow's first design, right after the existing width/bbox check:

- **Typed value.** `?g4e2e=1` is armed from the very first `design/new` navigation (Studio.tsx always passes
  `interactive` to `ShelterViewer`; the query param alone gates the hook — no need to reload later for the 3D-click
  step). Typed "10" into the Openings panel's South-window `NumberInput` (`getByRole('spinbutton', {name: 'South
  window'})`, disambiguated from the slider the same way as above), pressed Enter. Checked: (a) the field shows the
  committed value; (b) the 3D model changed — via a **local pixel-patch diff** at `window:S`'s own
  `?g4e2e=1`-projected screen position (`patchDiffScore`, new helper next to `png.mjs`'s `edgeBBox`), *not* a
  whole-canvas silhouette bbox: a window is an interior surface detail, not a change to the building's outer
  extent, so `edgeBBox` (used for Q1's width check) reported **zero** difference on the first attempt — confirmed
  by inspection, not assumed, before switching techniques; (c) a `page.on('requestfinished')` counter for
  `POST /api/simulate/preview` incremented after the 400 ms debounce (`Studio.tsx`'s `useDebouncedRequest(design,

**Script-methodology gotcha (not a product bug — two, actually, both worth recording so they aren't rediscovered).**
1. The popover-state click (`window.__g4PartScreenPosition('window:S')` + `page.mouse.click`) was first attempted
   right after the `studio-2storeys` capture loop, which leaves the viewport at its last iteration's width — 390px.
   At 390px the window's projected screen position can land outside that (narrower) canvas rect entirely, so the
   click missed and nothing got selected (verified: `debug-popover.mjs`, an isolated repro, showed the identical
   click sequence succeeding once the viewport was first reset to 1440 before computing/clicking). Fixed by an
   explicit `setViewportSize({width:1440,...})` immediately before the hook lookup + click, regardless of whatever
   the previous capture loop left the viewport at.
2. The very first Landing screenshot pair (`landing-1440-light`/`-dark`) initially came out **one theme click
   behind** — `-light.png` showed the previous page's dark theme still applied (and the toggle itself correctly
   showing Dark selected, i.e. genuinely not-yet-clicked, not a rendering desync), `-dark.png` showed light. Two
   independent isolated repros of the exact preceding sequence (post-`?g4e2e=1` Studio navigation, a focused
   uncommitted `NumberInput`, then `goto('/')`) could **not** reproduce it even once — `attr`/`localStorage`/
   `checked` all agreed within 50 ms of the click every time in isolation — so this reads as this script's own
   timing flakiness after ~24 prior screenshots/re-renders in one long-lived tab (GC/WebGL context pressure), not a
   `ThemeToggle`/`useForceDarkTokens` bug (the latter only ever touches the DOM `data-theme` attribute directly,
   never the `useTheme()` React state the toggle's own checked-radio rendering reads — confirmed by reading both
   files). Fixed pragmatically by raising the post-click settle wait from 200ms to 500ms everywhere in the script;
   re-ran clean (every theme/page pair correctly matched) on the next attempt.

**New finding from this pass (not a carried item — found while reading `geometry.ts` to understand why the dome
screenshots showed no window at all despite a 30% WWR).** `apps/studio/src/viewer/geometry.ts`'s `windowRect()`
(used by both the box/cylinder walls and `domeFacetsFor`) clamps the window's height to
`facadeHeightOrSlantHeight - WINDOW_SILL_M(0.9m) - WINDOW_LINTEL_MARGIN_M(0.3m)`, i.e. requires 1.2m of clearance
regardless of WWR. For a dome, "facade height" is a wall-BAND's **slant height** (`domeFacetsFor`, `dz = r/3`),
which is only ≈0.85m for the default/min-ish 5m-diameter dome (`r=2.5`, band 0's `dz≈0.83`, `slantHeight≈0.85`) —
below the 1.2m floor, so `windowRect` returns `null` for **every** dome facet at **every** WWR value, silently. The
server-side engine is unaffected (`assemble.ts`'s spherical-zone area formulas have no such margin, confirmed by
the "Sun through windows" heat-flow figure changing correctly with WWR in every dome screenshot, e.g. +11.1 kWh at
30% WWR — the simulation is correct, only the 3D preview is misleading). Verified the root cause, not just
guessed at it: `<scratchpad>/q2/screenshots/verify-dome-5m.png` (no window, 30% WWR) vs. `verify-dome-12m.png`
(same WWR, diameter raised to 12m — a window clearly appears) via a small throwaway script
(`<scratchpad>/q2/verify-dome.mjs`). Threshold: band-0 slant height ≈ `r/3`, so domes need roughly ≥7.2m diameter
before a window can render at all — well above the 5m default, so a first-time user configuring a dome with any
WWR sees no window regardless of the slider value.
