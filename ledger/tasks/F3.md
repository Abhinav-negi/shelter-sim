# F3 — Studio page: controls, live preview, results
Status: DONE      Depends on: F1, F1b, F2, P2 (all merged)

## Goal
The core design experience: controls → store → 3D model, with a debounced preview simulation and results that
explain the outcome.

## Read
`ledger/PLAN.md` (§Client, §Results) · `apps/studio-server/API.md` · `apps/studio/src/{design,api,viewer}/**` ·
`apps/client/src/features/results/{explain.ts,labels.ts}` (port the logic, not the UI)

frozen. **No npm install.**

## Conditions
1. Control groups: Environment (preset/custom location via search, date), Geometry, Materials (material + thickness
   per surface), Openings (WWR per facade, glazing, shutters), Orientation (dial), Advanced (occupancy). Ranges come
   from `/api/options`.
2. Each change updates the 3D model immediately and triggers a preview 400 ms after the last change. Stale responses
   are discarded (AbortController).
3. The status shows the real stages, not timers. Errors say what happened and offer a retry. Custom-location weather
   provenance notes are visible.
4. Results: indoor vs outdoor chart (°C, thermal colours), heat-flow pathway breakdown (daily kWh), the engine KPIs
   listed in PLAN.md, and "What happened / Why" from the ported explain logic. No invented metrics.
5. Save design / Save run (P2 routes) persist the design and the run.
6. Screenshots at 1440 and 390 px, light and dark. No console errors.

## Rules
Do not expose every engine variable. Advanced stays collapsed. Units are always shown in mono.

**Two real bugs found and fixed during live QA (both within/adjacent to allowed scope, not viewer/store/server):**

1. **Save run was broken (500, condition 5).** `apps/studio/src/api/client.ts`'s `request()` unconditionally sent
   `Content-Type: application/json`, even for `POST /api/designs/:id/simulations` (API.md §9: no request body).
   Fastify's default JSON body parser rejects a `Content-Type: application/json` request with an empty body
   (`FST_ERR_CTP_EMPTY_JSON_BODY` → 500 `INTERNAL_ERROR`) — confirmed via the scratch server's `console.error` stack
   trace (logger is off, so this only surfaces server-side; the client just sees a generic 500). `client.ts` isn't
   in F3's "may touch" list, but this is exactly the "one-line wiring fix elsewhere in apps/studio/src" the brief
   allows for — the bug is entirely in this shared fetch wrapper, not in a frozen file, and condition 5 cannot pass
   without it. Fix: only set the JSON content-type header when `init.body !== undefined`. This changed the exact
   `fetch` call shape for every body-less request (GET/DELETE/logout/runSimulation), so the 6 pre-existing api-wrapper
   test files (`auth.test.ts`, `designs.test.ts`, `health.test.ts`, `locations.test.ts`, `options.test.ts`) had their
   `toHaveBeenCalledWith(...)` assertions updated to match — they were asserting the buggy behaviour, not a real
   contract; nothing about *what* is sent (method/URL/body) changed, only that the header is now sent conditionally.
   `previewSimulation`/`createDesign`/`updateDesign`/login/register (all of which do send a body) are unaffected.
2. **Heat-flow chart: value label overlapping the row's category label (condition 6 visual QA, both light/dark,
   1440 px).** `HeatFlowChart.tsx` used recharts' `LabelList position="right"`, which anchors the label beyond the
   bar's tip *in the value's own direction* — for a large-magnitude **negative** bar (e.g. "Radiated to night sky"
   at −138.6 kWh) that direction is further left, past the tip, landing the number directly on top of the row's own
   axis label text (visually merged, e.g. "Radiated to nigh138.6 kWh"). Root cause + fix: an SVG rect's `x`/`width`
   are always non-negative (`x` = the smaller of the two scaled endpoints), so `x + width` is always the bar's true
   screen-right edge — the tip for a positive bar, the zero line for a negative one — and is never further left than
   the plot's own zero reference. Replaced the built-in `position="right"` with a small custom `content` renderer
   (`ValueLabel`) that anchors there directly. Verified by screenshot: all labels (positive and negative, including
   the two large negative ones that previously collided) now sit cleanly to the right of their bars with no overlap,
   at both 1440 and 390 px, light and dark.
3. **390 px header overflow (condition 6).** The Studio header row (name input + save-state label + 2 buttons) was
   a single non-wrapping flex row; at 390 px the two buttons ("Save design"/"Save run") and the status label left
   almost no room for the name input, truncating "Untitled shelter" to ~5 visible characters. Fixed in
   `routes/Studio.tsx`: the row is now `flex-wrap`, and the name input is `basis-full` below the `sm` breakpoint
   (own line) and `flex-1` at `sm:` and up (original single-line layout, unchanged on desktop). Verified: 390 px now
   shows the full name on its own line with the status/buttons wrapping below it; 1440 px is pixel-identical to
   before (single line, unchanged).

**Review round 2 (orchestrator, e9e0211) — condition 6 rejected, three real bugs in my own screenshots I'd missed.**
All three were genuine, all fixed in `routes/Studio.tsx` and `results/HeatFlowChart.tsx` only (still no viewer/store/
server edits):

1. **Viewer framing broken (the centre pane showed only a giant roof plane).** Root cause, confirmed by the
   reviewer's hypothesis and by inspection: `AppShell.tsx`'s outer wrapper is `min-h-screen` (a *minimum*, not a
   cap) and `Studio.tsx`'s own root was `flex-1` with no hard height anywhere above it. With a tall controls column
   (six sections' worth of fields), the whole page grew taller than the viewport and the *document* scrolled instead
   of the page's own panes — and the viewer pane, being an ordinary flex child of that unbounded column, took on
   whatever height its tallest sibling (controls) forced, stretching the `<Canvas>` very tall and narrow. The
   camera's FOV/distance are tuned for a normal aspect ratio (correct in `/dev/viewer`, which isn't inside this
   flex chain), so on that stretched canvas only a thin high-up slice of the scene — the roof — fell inside the
   frustum. Not a viewer-internals bug; fixed entirely in `Studio.tsx`, which I'm allowed to touch, per the
   reviewer's own suggested shape of fix (a measured `h-[calc(100dvh-<header>)]`), without touching the shared
   `AppShell.tsx` (used by every route, out of scope and higher-risk to change). Measured the real `AppShell` header
   height via `getBoundingClientRect()` in headless Chrome: 53.66 px at both 1440 and 390 (padding-driven, not
   width-driven) → rounded up to 56 px for safety margin. `StudioLoaded`'s root div is now
   `h-[calc(100dvh-56px)] flex-col overflow-hidden` instead of the old unbounded `flex-1`; every already-present
   `min-h-0`/`flex-1` further down the tree now means something, because there's finally a real ceiling above it.
   Verified: the whole building, compass, and sun line are visible at 1440×900 (both a 5×5 m and, via the flow
   test's edited 18×5 m design, an extreme aspect ratio — both frame correctly, confirming this was never about the
   building's own size, only the canvas's).
2. **Heat-flow chart labels still overlapping / clipping.** My round-1 fix (anchor at the bar rect's `x+width`)
   removed the *axis-label* collision but not the *bar* collision (a short bar's label could still land on/against
   its own fill) and didn't reserve enough right margin for the longest string at 390 px ("+225.5 kWh" clipped to
   "kV"). Rather than tune offsets a third time, restructured `HeatFlowChart.tsx` to not use recharts'
   `BarChart`/`LabelList` at all: each pathway is now two plain flexbox lines — the category label alone on its own
   full-width line, then a thin bar (a zero-referenced `<div>` positioned by percentage against a shared min/max
   domain, gain vs loss by direction + opacity, same as before) with the kWh value in a dedicated fixed-width
   (`w-24`) right-aligned mono column that the bar's track can never reach into. This removes the entire class of
   bug structurally (label vs. category text and label vs. bar-fill can no longer compete for the same pixels,
   regardless of sign or magnitude) instead of re-deriving SVG anchor math a third time. `recharts` is no longer
   imported by this file (still used by `TemperatureChart.tsx`, unaffected); `ResultsPanel`'s lazy chunk shrank
   ~22 kB as a result. Verified at both 1440 and 390, light and dark, and specifically the two previously-flagged
   large-negative bars plus the smallest bar and the largest positive one (the one that clipped) — all clean.
3. **390 px: the 3D model wasn't visible on the first screen.** Was a consequence of bug 1 (unbounded page height
   meant the natural stacking order — controls, then viewer, then results — put the tall controls column first).
   With the page now height-capped, restructured the controls/viewer/results row: the viewer's JSX moved to be
   *first* in the DOM (own line, mobile default `order`) at a fixed `h-[45vh] shrink-0` so its aspect ratio stays
   sane regardless of controls/results height, with `overflow-y-auto` on the row itself so mobile is one natural
   scrolling column (viewer, then controls, then results). At `lg:` and up, `lg:order-1/2/3` restores the original
   visual Controls|Viewer|Results layout (unchanged from before — 1440 screenshots are laid out identically to
   round 1) and each pane switches to `lg:overflow-y-auto`/`lg:overflow-hidden` independent scrolling. Verified: the
   full 3D model is the first thing visible under the header at 390 px, in both themes.
