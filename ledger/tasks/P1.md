Status: DONE      Depends on: S0

## Goal
Create `apps/studio-server` (workspace `@shelter/studio-server`, Fastify 5, :4100): the `ShelterDesign` type and
validation, a copied and extended assembly pipeline, the `SimulationProvider` seam, `/api/health`, `/api/options`,
`/api/simulate/preview`, and `API.md`. This task fixes the contract that every other task builds on. It also

## Conditions
1. `src/design/types.ts` exports `ShelterDesign`, `DesignLocation`, `SurfaceConstruction`, `Options` (and the
   preview response type) exactly as in PLAN.md §ShelterDesign. `package.json` has `"types"` pointing at it, so the
   client can `import type`.
2. `src/design/assemble.ts` is a copy of `apps/server/src/assemble.ts` with a header comment naming its origin, plus:
   `azimuthDeg → building.azimuth`; `{materialId, thicknessM}` single-layer constructions using the given thickness;
   `location.kind==='custom'` accepted through an injected `weatherFor(location)` parameter (P3 implements the
   real one; P1 throws a typed `CUSTOM_LOCATION_UNAVAILABLE` error when none is provided). Keep `skyModel:'isotropic'`.
3. **Parity test:** converting `apps/server/test/fixtures/leh-default.json` `.input` to a ShelterDesign
   (preset location, azimuth 0, constructions null) and assembling it must give a `canonicalRequestHash` equal to the
   old `apps/server/src/assemble.ts` `assemble(input)`, which the test imports by relative path, read-only.
4. `POST /api/simulate/preview` returns `{kpis, result}` (`resultToJson`) for the default design. Rotating
   `azimuthDeg` 0→90 changes `kpis.meanIndoorTemp`. `wallConstruction.thicknessM` 0.2→0.6 changes the result.
5. Validation mirrors the old server: an ajv schema, `VALIDATION_ERROR` with a dotted `field`, the engine
   `STATUS_BY_CODE`, a 5 MB limit, and no stack traces. Ranges: azimuth −180..180, thickness 0.02..1.0 m, plus the
   old DesignInput ranges.
6. `src/providers/`: `SimulationProvider` interface + `fastPhysics` (id `'fast-physics'`, wraps `simulate`). Routes
   call the provider, never `simulate` directly.
7. `GET /api/options` = the old options (ported), with `defaults` as a ShelterDesign and `ranges` for every numeric
   control.
8. `src/env.ts` reads `PORT` (default 4100), `HOST`, `MONGODB_URI`, `JWT_SECRET`, `NODE_ENV`. The DB and auth
   variables are optional in P1 (P2 makes them required at startup). `.env.example` is committed with names only.
   `npm run dev -w @shelter/studio-server` starts on :4100 without a DB.
9. `API.md` documents every P1 route plus the planned P2/P3 routes, marked `(P2)` / `(P3)`.
10. `npm test -w @shelter/studio-server` passes. `npx tsc -p apps/studio-server --noEmit` is clean. The old suites
    `npm test -w @shelter/server` still pass. The frozen-app guard diff is empty.

## Rules
Use the old server's conventions (ESM, `.js` import suffixes, `tsx`, vitest, `buildApp()` + `app.inject` tests).
Keep it small: no DI container, no factories, no controller classes. Use a `ponytail:` comment for any deliberate
shortcut.

**Dependencies installed** (only installer in this batch, exactly the list given): `fastify
@fastify/jwt @fastify/cookie mongoose` (dependencies), `tsx mongodb-memory-server` (devDependencies).
`npm install ... --workspace @shelter/studio-server` deduped fastify against `apps/server`'s already-

`mongodb-memory-server` are installed but UNUSED in P1 code (no route touches Mongo yet); they're here
so P2 never touches the lockfile, per the brief.

**Decisions + why:**
- `ShelterDesign`/`DesignLocation`/`SurfaceConstruction`/`Options`/`PreviewResponse` all live in
  `src/design/types.ts`, and `package.json`'s `"types"` field points straight at that `.ts` file (no
  build step for this package — it runs under `tsx`, same as `apps/server`). `PreviewResponse.kpis`
  is typed as `@shelter/engine`'s `SimulationKpis` (a real, useful type-only import the client is
  allowed to take); `result` stays `unknown` because `resultToJson`'s own return type is `unknown` —
  the JSON shape is documented in prose in `API.md` §4, same convention `apps/server/API.md` uses.
- `src/design/assemble.ts` is condition 2's literal copy of `apps/server/src/assemble.ts` plus the
  three deltas named in the task file. `defaultThicknessM`/`THICKNESS_OVERRIDE_M`/
  `DEFAULT_THICKNESS_BY_CATEGORY` were deleted (not ported) — with `thicknessM` now given directly by
  the caller, that lookup table has no caller left; kept it out rather than leaving dead code.
- `weatherFor` is `(customLocation) => {weather: WeatherSeries (full year), site: Site}` — the SAME
  shape as the preset branch's `tmyById` + `siteForLocation`, sliced to the day by `assemble` itself
  in both branches. This is a guess at P3's future seam (P3's own task file just says "plug it into
  P1's `weatherFor(location)` hook") but keeping the two branches symmetric seemed like the least
  surprising contract; P3 owns `app.ts`/`design/assemble.ts` too and can reshape this if the real
  Open-Meteo/cache flow wants something else — it's a seam, not a frozen contract.
- `CustomLocationUnavailableError` is a plain `Error` subclass with a literal `code` field (NOT an
  `@shelter/engine` `EngineError` — that class's `code` is typed to the engine's own closed
  `EngineErrorCode` union, which `CUSTOM_LOCATION_UNAVAILABLE` isn't part of). Mapped to HTTP 422 in
  `app.ts`'s error handler, documented in `API.md` §6.
- `building.azimuth = design.azimuthDeg` is applied right after weather/site resolution, before
  `setSize`/materials/WWR — order doesn't matter physically (azimuth only rotates at solve time,
  `packages/engine/src/solve/assemble.ts:121`) but this keeps a clear, single "new step" in the
  assemble pipeline instead of threading it through the copied steps.
- `GET /api/options.ranges` is new (condition 7): one `{min,max,step?}` per numeric control,
  including the new `azimuthDeg` (-180..180) and `thicknessM` (0.02..1.0) ranges from the task file,
  plus the old `DesignInput` ranges (length/width/height/wwr) carried over from
  `apps/server/src/app.ts`'s `designInputSchema()`.
- ajv nullable-object trick for `wallConstruction`/`roofConstruction`/`floorConstruction`:
  `type: ['object','null']` + `required`/`properties` — JSON Schema's `required`/`properties` only
  constrain instances that are actually objects, so a `null` value skips them and validates. Same
  pattern `apps/server/src/app.ts` already uses one level up for `wallMaterialId: string|null`.

**Gotchas:**
- `apps/studio-server/tsconfig.json` could NOT keep `"rootDir": "."` (copied from `apps/server`
  verbatim at first) — the parity test imports `apps/server/src/assemble.ts` by relative path
  (condition 3 requires this, read-only), which sits outside `rootDir: "."`, and `tsc -p
  apps/studio-server --noEmit` failed with TS6059. Fix: drop the `"rootDir"` override entirely (base
  config doesn't set one either) and let TS infer the common root; `noEmit: true` means this has no
  effect on any emitted output. Everything else in `tsconfig.json` is a straight copy of
  `apps/server`'s.
- Fixture `apps/server/test/fixtures/leh-default.json` is 287 KB — too big for a normal file-read
  tool call, and no `resolveJsonModule` is set anywhere in this package's tsconfig chain (adding it
  would mean touching `tsconfig.base.json`, frozen). Loaded it in the parity test with
  `readFileSync` + `JSON.parse`, the same pattern already used by
  `packages/engine/test/{storage,pcm}.test.ts` for reading source files at runtime — no tsconfig
  change needed.
- First `npm install ... --workspace @shelter/studio-server` printed `npm warn workspaces
  @shelter/studio-server in filter set, but no workspace folder present` even though the folder and
  `package.json` already existed — harmless in this case (verified after: correct deps landed in
  `apps/studio-server/package.json`'s own `dependencies`/`devDependencies`, `package-lock.json` gained
  an `apps/studio-server` workspace entry, fastify deduped to the existing `5.12.5`, no stray
  `node_modules` inside `apps/studio-server`). Root cause not chased further since the actual state
  came out correct; flagging in case a later installer in this batch hits the same warning and needs
  to know it's not necessarily a real failure.
