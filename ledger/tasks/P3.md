# P3 — Weather + location search (custom locations)
Status: DONE      Depends on: P1

## Goal
Any lat/lon becomes simulatable. Search places via Open-Meteo geocoding, fetch a year of hourly weather, normalise it
with `@shelter/data`, cache it in Mongo, and plug it into P1's `weatherFor(location)` hook.

## Read
`ledger/PLAN.md` (§Custom location) · `apps/studio-server/src/design/assemble.ts` · `packages/data/src/weather/{sources.ts,pipeline.ts}` (exports + header comments)

## May touch / must not touch
May: `apps/studio-server/src/{weather/**,locations/**,app.ts}`, `test/**`, `API.md`. Must not: anything else.
**No npm install.** Use global `fetch`, which is injectable for tests.

## Conditions
1. `GET /api/locations/search?q=` returns `[{name, country, admin1, lat, lon, elevation}]` (≤8) from the Open-Meteo
   geocoding API. Upstream failure → 502 `UPSTREAM_UNAVAILABLE`.
2. A custom-location preview works end to end: fetch a full reference year (Open-Meteo archive, falling back to NASA
   POWER), build it with the data package's URL builders and parsers, then `normaliseWeather`, then slice the day.
   `groundTempMeanAnnual` = the annual mean. `standardMeridian` = `utc_offset_seconds/3600*15`. `groundAlbedo` 0.2.
3. A `weatherCache` Mongo model keyed by `{source, lat(2dp), lon(2dp), year}`. The second request makes no network call
   (test it with a counting fake fetch).
4. The preview response for a custom location includes `weatherProvenance {source, year, notes[]}` listing the
   assumptions (meridian, albedo). API.md is updated.
5. All tests use a fake fetch (a recorded fixture), with no live network in CI. One optional live smoke test is skipped
   unless `LIVE=1`.

## Rules
Never invent weather values. If both sources fail, return an error; there is no fallback to a preset site.

**Decisions + why:**
- **The seam is exactly P1's, unchanged.** `weatherFor: (location) => {weather, site}` stays
  synchronous. `resolveCustomWeather(location, fetchImpl?)` in `src/weather/resolve.ts` is the async
  half: `app.ts`'s preview route, for `location.kind==='custom'`, `await`s it BEFORE calling
  `assemble()`, then passes `() => ({weather: resolved.weather, site: resolved.site})` as
  `weatherFor`. `design/assemble.ts` was not touched at all -- P1's seam shape needed no change.
- **Timezone gotcha (the brief's hint, confirmed):** `packages/data/src/weather/sources.ts`'s
  `openMeteoUrl` (frozen) issues no `timezone` param, so a plain call returns UTC `hourly.time` with
  no offset to read. Fix: append `&timezone=auto` to the builder's own URL string in
  `resolve.ts`'s `tryOpenMeteo` (can't touch the frozen builder). This does two things at once: (a)
  the response gains a top-level `utc_offset_seconds` -> `standardMeridian = utc_offset_seconds/3600*15`;
  (b) `hourly.time` becomes genuinely local, matching `RawWeather.startHour`'s documented contract
  ("local clock hour") -- without it, `parseOpenMeteo`'s `startHour`/day-of-year would silently be
  wrong (UTC mislabelled as local), not just the meridian. Verified live: Shimla (31.10442, 77.16662)
  -> `utc_offset_seconds: 19800` (IST, +5:30) -> `standardMeridian = 82.5`, matching Leh's bundled
  `siteForLocation` value (82.5, IST) as a sanity check.
- **NASA POWER fallback meridian:** NASA POWER's hourly endpoint has no offset field at all, but its
  header declares `time_standard: "LST"` (Local Standard Time) -- i.e. the response is already in the
  fixed-width standard time zone for that longitude, whose meridian is by definition the nearest
  multiple of 15°. Used `standardMeridian = Math.round(longitude/15)*15` for that branch only.
  Documented in both `resolve.ts`'s header comment and `API.md` §4.
- **groundTempMeanAnnual** = arithmetic mean of the normalised year's `T_amb` (K), computed AFTER
  `normaliseWeather` (so it's the gap-filled/resampled series, not the raw fetch) -- mirrors
  `design/assemble.ts`'s own `annualMeanK` for the preset branch, reimplemented locally in
  `resolve.ts` (5-line function; not worth exporting/importing across a module that P3 doesn't own).
- **groundAlbedo = 0.2**, a fixed constant (PLAN.md "Custom location"), disclosed as a
  `weatherProvenance.notes` line rather than silently applied.
- **Rule ("never invent weather values ... no fallback to a preset site"):** `resolveCustomWeather`
  tries Open-Meteo, then NASA POWER, and on both failing throws `UpstreamUnavailableError` (502
  `UPSTREAM_UNAVAILABLE`) -- there is no third branch. Fallback triggers on ANY Open-Meteo-path failure
  (network error, non-2xx, parse error, or a `normaliseWeather` `WEATHER_INVALID` validation failure),
  not just the network call, since from the caller's perspective all of those mean "this source
  didn't produce usable weather" equally.
- **weatherCache** (`src/weather/cache.ts`): keyed by `{source, lat(2dp), lon(2dp), year}` (unique
  index), using mongoose's default connection -- no `src/db.ts` created (P2 owns that, running in
  parallel; ledger conflict-avoidance rule). `WeatherSeries`'s numeric fields are `Float64Array`
  (`packages/engine/src/types.ts`), which Mongoose/BSON don't round-trip as themselves, so
  `serialiseWeather`/`deserialiseWeather` convert to/from plain `number[]` at the cache boundary only
  -- every other module still sees real `Float64Array`s. `standardMeridian` is cached ALONGSIDE the
  weather series (not recomputed) specifically so a cache hit needs zero network calls, including no
  re-derivation of the offset (condition 3's own wording: "the second request makes no network
  call"). Degrades via `mongoose.connection.readyState !== 1` check at the top of both read and
  write: not connected -> read returns `undefined` (falls through to fetch), write is a no-op. Guarded
  model registration (`mongoose.models['WeatherCache'] ?? mongoose.model(...)`) against
  `OverwriteModelError` on a hot-reloaded dev server.
- **`buildApp({ fetchImpl? })`**: the only signature change to `app.ts`'s public surface. Threaded
  into both the locations plugin (`app.register(locationsRoutes, fetchImpl ? {fetchImpl} : {})`) and
  `resolveCustomWeather(design.location, fetchImpl)` in the preview route. Production `index.ts` still
  calls plain `buildApp()`; `fetchImpl` stays `undefined` and every default parameter along the chain
  falls through to the real global `fetch`. This is what makes fixture-based, no-live-network testing
  possible at the ROUTE level (not just by unit-testing `resolveCustomWeather` in isolation).
- **`UpstreamUnavailableError`** (`src/weather/errors.ts`): same shape/convention as P1's
  `CustomLocationUnavailableError` (plain `Error` subclass, literal `code`), shared by
  `geocode.ts`'s `searchLocations` (condition 1's 502) and `resolve.ts`'s "both sources failed" case
  -- one error type for "an upstream weather/geocoding service is unreachable", mapped once in
  `app.ts`'s error handler.

**Gotchas:**
- `app.register(locationsRoutes, { fetchImpl })` failed `tsc` under this repo's
  `exactOptionalPropertyTypes: true` (`fetchImpl: typeof fetch | undefined` isn't assignable to an
  optional-but-not-`|undefined` property type). Fixed with `fetchImpl ? {fetchImpl} : {}` at the call
  site rather than loosening the plugin option's type.
- `sources.ts`'s local `RawWeather` (used by `parseOpenMeteo`/`parseNasaPower`'s return type) and
  `pipeline.ts`'s exported `RawWeather` (the only one `@shelter/data`'s index re-exports) are two
  separate declarations the package's own header comment says are "kept structurally IDENTICAL" --
  confirmed field-for-field; `normaliseWeather`'s parameter accepts the parsers' return values with no
  cast needed, purely by structural typing.
