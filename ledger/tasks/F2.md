# F2 — ShelterViewer (3D)
Status: DONE      Depends on: F1

## Goal
A view-only R3F scene that renders the current ShelterDesign truthfully and updates immediately on every change.

## Read
`ledger/PLAN.md` (§3D viewer) · `apps/studio/src/design/store.ts` · `apps/studio-server/src/design/types.ts` ·
`apps/studio-server/API.md` (§options: materials/preset constructions, so thickness can be derived)

## May touch / must not touch
May: `apps/studio/src/viewer/**` (+ one demo route if needed). Must not: the store API (ask the orchestrator), server,
frozen paths. **No npm install.**

## Conditions
1. Pure `src/viewer/geometry.ts`: ShelterDesign → dimensions, wall thickness (the construction's `thicknessM`, or the
   preset stack's total when null), window rectangles per facade from WWR, azimuth. Vitest: width 4→6 m makes the
   mesh wider; thickness 0.1→0.2 m makes the walls thicker; azimuth 0→90 rotates the group.
2. The scene has a ground, a flat roof, walls with real openings (no z-fighting), a compass (N marked), and a sun
   direction from date + lat/lon + an hour prop (a small solar-position function). Shadows are on.
3. OrbitControls: orbit, zoom and pan, with a clamped polar angle (it can't go under the ground). No picking, no gizmos,
   no pointer editing.
4. `frameloop="demand"`. It rerenders only on design or hour changes, and geometry is memoised. No console
   warnings.
5. Screenshots of 3 designs (default, wide + thick, rotated 90°). The model reads as architectural and precise:
   restrained materials and neutral light, no toy look.

## Rules
The model reflects only what the physics models. There is no roof-type control and no decorative props.

## Evidence

**Files.** `apps/studio/src/viewer/geometry.ts` (+`geometry.test.ts`), `solar.ts` (+`solar.test.ts`),
`useThemeColors.ts`, `Building.tsx`, `Compass.tsx`, `ShelterViewer.tsx`, `DevViewer.tsx`; `apps/studio/src/design/useOptions.ts`
(new); `apps/studio/src/App.tsx` (+1 import, +1 lazy() const, +1 `<Route path="/dev/viewer">`); `STUDIO.md` (F2 row).

**geometry.ts (condition 1).** Pure `buildSceneGeometry(design, options) -> SceneGeometry`: dimensions,
`wallThicknessM`/`roofThicknessM`/`floorThicknessM` (construction override `.thicknessM` else
`options.presets[presetId].thicknessM.{wall,roof,floor}`, with a defensive `0.3` fallback if the preset id isn't
found — shouldn't happen, but the viewer shouldn't throw on a transient state), a `WindowRect{width,height,sill}`
per facade (area = WWR × facadeWidth × heightM, aspect 1.3 landscape, clamped to fit with a 0.15 m side margin, a
0.9 m sill and a 0.3 m lintel margin — reasonable architectural constants, not spec'd numbers), and `rotationY`
(radians, three.js `group.rotation.y`). 6 vitest cases cover exactly the 3 named checks (width 4→6 widens the E/W
facades, thickness 0.1→0.2 thickens the walls, azimuth 0→90 rotates the group to `-π/2`) plus preset-thickness
fallback and window clamping/zero-WWR.

**World frame + azimuth sign convention (documented at length in geometry.ts's header — read that for the full
derivation).** World: Y up, +X = East, +Z = South — chosen to match the *engine's own* documented convention
(`packages/engine/src/solar/geometry.ts`: "azimuth measured from south, negative = East, positive = West", and
`packages/engine/src/solve/assemble.ts`'s surface azimuths: S=0, E=-90, W=90, N=180). `azimuthDeg` composes as
`surfaceAzimuth + building.azimuth` in the engine, so a positive `azimuthDeg` moves the wall that used to face
south toward west — confirmed against `apps/studio-server/API.md` §3's own comment ("positive = toward west").
Solving for three.js's right-handed `Ry(theta)` (which sends local +Z to `(sin theta, 0, cos theta)`) against
"local south (+Z) should end up pointing toward -X (west)" gives `theta = -azimuthDeg`. `rotationY = -azimuthDeg`
(radians). Verified visually: at azimuthDeg=90 the window (on the design's S-facing wall) rotates out of view from
the default south-east camera, as expected if it now faces west (`rotated90-light` screenshot).

**solar.ts (GEOMETRY TRUTH / condition 2's sun direction).** A small pure `sunAngle`/`sunDirection` — declination
(Cooper 1969), equation of time (Spencer 1971), hour angle, atan2 altitude/azimuth — the *same formulas* as
`packages/engine/src/solar/geometry.ts`, reimplemented rather than imported: the client only imports **types**
from `@shelter/engine` (API.md §0, SUBAGENT RULES §2), so this is a second, independent implementation, not a
shared runtime dependency. Verified correct by reproducing the engine's own doc-commented reference figure — Leh,
winter solstice, noon altitude 32.4° — to within 0.1°. **Flag (rule 1):** F2.md's own example ("solar noon at Leh
34.16N in mid-January has elevation ≈32°") doesn't hold under Cooper's declination — mid-January (day 15) peaks at
~34.6°, not ~32°; 32.4° is specifically the *winter-solstice* (21 Dec) figure, which is what the engine's own doc
comment cites. `solar.test.ts` uses the solstice date so the assertion is checked against an independently
verified number rather than picking a January date that would need a suspiciously wide tolerance to pass. Not
treated as blocking — noted per rule 1 in case a reviewer wants the January wording changed instead.
`approximateStandardMeridian` (nearest 15° to longitude) is a documented, deliberate simplification (`ponytail:`
comment in solar.ts) — the browser has no server round trip for the site's real UTC-offset meridian for a preset
location; it only shifts *when* solar noon falls by up to ~30 min, not the noon altitude, and this function is
purely a decorative viewer indicator, never fed back into the physics engine.

**Scene (condition 2).** `Building.tsx`: each wall is up to 5 non-overlapping boxes (2 piers, sill band, lintel
band, all sharing the wall's `wallThicknessM` depth) framing the window opening — no CSG, so nothing is coplanar
and nothing z-fights; the glass pane is a separate thin inset box showing the reveal depth. Flat roof + floor
slabs, flush with the wall footprint (no eaves — F2.md Rules: no roof type control, the engine only knows flat).
Ground: a large fog-faded disc (`ShelterViewer.tsx`'s `fog`/`groundRadius`) so its edge doesn't read as a hard
"tabletop" horizon. Compass (`Compass.tsx`): a ring + needle + Billboard-wrapped box-built "N" glyph, positioned
from `geometry.lengthM`/`widthM` but **not** a child of the azimuth-rotated `<group>` — confirmed independent of
building rotation in the `rotated90-light` screenshot (compass unchanged, building rotated). Sun: `directionalLight`
positioned along `sunDirection(...)  * distance`, `castShadow`, shadow-camera sized to the footprint; a
`hemisphereLight` + `ambientLight` fill so shadows aren't pure black. Verified live (not just visually static):
`hour=8` vs `hour=16` screenshots show the shadow swinging from NW to SE, confirming `hour` actually drives
`sunDirection` (not stale-memoized).

**Bug found + fixed during visual QA: light color vs. theme color.** First pass used `colors.paper` (the
paper/ink design token, correctly near-black in dark mode for UI chrome) as the `directionalLight`/`hemisphereLight`
**color**, not just the background. Result: dark-theme screenshots rendered almost fully black — the "sun" was
lighting the scene with near-black light, and separately the building's own `meshStandardMaterial` used
`colors.surface` (also near-black in dark mode) as its base albedo, which stays dark under any light intensity.
Fixed by decoupling three things that don't all vary with the UI theme: (1) light source colors are now fixed
constants (`SUN_COLOR`/`SKY_COLOR` in ShelterViewer.tsx) representing physical daylight — a UI theme toggle
shouldn't turn off the sun; (2) the building's own material palette (`WALL_COLOR`/`ROOF_COLOR`/`FLOOR_COLOR`/
`EDGE_COLOR` in Building.tsx) is now a fixed, theme-independent "restrained neutral daylight" palette — a real
shelter's plaster doesn't recolor when someone toggles dark mode; (3) only the **backdrop** (Canvas background,
fog, ground plane, compass accent) still follows `useThemeColors()` so the viewport harmonises with the
surrounding UI chrome, which is what F2.md's "use the design tokens for scene colours so light/dark themes
match" is read to mean. Documented at length in both files' headers/comments for whoever touches this next.

**Camera framing** iterated once after the first screenshot pass looked too close-in/table-top (roof filling
most of the frame, hard-edged ground horizon visible): pulled the default camera back (`camDist` factor
1.4→2.1, fov 32→28) and enlarged+fogged the ground disc (radius footprint×6→×16, `fog` near/far at ×4/×11) so it
reads as an open ground plane, not a disc.

**Condition 3 (OrbitControls).** `<OrbitControls makeDefault>` with `minPolarAngle=0.15`, `maxPolarAngle=π/2-0.02`
(can't go under the ground or flip over the top), `minDistance`/`maxDistance` scaled to the footprint. No gizmo,
no picking, no `onClick`/`onPointerDown` handlers anywhere in `viewer/**`.

**Condition 4 (frameloop=demand, memoised, no console warnings).** `Canvas frameloop="demand"`. `buildSceneGeometry`,
`resolveLatLon`, `sunDirection` are each `useMemo`'d on their actual dependencies (`[design, options]` /
`[lat, lon, design.date, hour]`), and React-three-fiber's reconciler invalidates automatically on every commit
(a design/hour prop change) — confirmed in `node_modules/@react-three/fiber`'s own source that drei's
`OrbitControls` also calls `invalidate()` on its `change` event, so no manual `invalidate()` call was needed
anywhere. Passed `shadows="percentage"` (not the boolean default) to avoid `three@0.186`'s removed
`PCFSoftShadowMap` constant triggering a runtime deprecation warning (`gl.shadowMap.type` mapping in
`@react-three/fiber`'s `events-*.js`) — fixed and verified gone.
**Console warnings, honestly reported:** the *only* remaining console output on a production build/preview is
one `THREE.Clock: This module has been deprecated. Please use THREE.Timer instead.` warning, traced to
`@react-three/fiber@9.8.1`'s own internal `new THREE.Clock()` call (`node_modules/@react-three/fiber/dist/
events-9ce18a08.esm.js:1054`) — every `<Canvas>` in this repo on the currently pinned `three@0.186.1` +
`@react-three/fiber@9.8.1` pair would emit it; it isn't caused by anything in `viewer/**`, and F2's brief
forbids `npm install` (so bumping fiber to a version built against three's `Timer` API isn't available). A
separate, worse warning ("Attempted to synchronously unmount a root while React was already rendering") only
appeared under the Vite **dev server** with React 19's `<StrictMode>` (main.tsx, frozen — not touched); it
disappeared entirely running the same build via `vite preview` (production, no StrictMode double-invoke),
confirming it's a dev-only React 19 StrictMode / react-three-fiber interaction artifact, not a real bug in this
code or in what ships. Final screenshot pass and the hour-8/16 sanity check were both run against the
production build for this reason.
