# G4 — Select-to-edit (3D part ↔ control)
Status: REVIEW (verified live by session 5, awaiting orchestrator spot-check)      Depends on: G3 (merged)      Phase: Studio v2 (`ledger/V2.md` §G4)

## Goal
Hover/click a wall, window, roof or floor in the 3D model → it highlights, and the matching left-panel section
opens, scrolls into view and highlights that field. Focusing/hovering a field highlights the part. A small floating
panel next to the selected part lets you type its key values.

## Conditions
1. `PartId = 'wall:S'|'wall:E'|'wall:W'|'wall:N'|'window:S'|…|'roof'|'floor'`; `hoveredPart`, `selectedPart` live in a
   UI-only store (never saved, never sent to the server).
2. Meshes carry their PartId; R3F pointer handlers `stopPropagation`; hover = subtle accent tint, selected = stronger;
   cursor becomes a pointer on hover; click empty space or Esc clears. Cylinder/dome facets map to their quadrant's
   `wall:<o>`; dome roof bands → `roof`. Viewer on Landing/Compare stays non-interactive (prop, default off).
3. Selecting a part opens its `Section` (controlled `open`), `scrollIntoView({block:'nearest'})`s the field and
   briefly highlights the `FieldRow` (accent hairline, fades). Mapping: `window:o` → Openings / "<o> window";
   `wall:*` → Materials / walls; `roof` → Materials / roof; `floor` → Materials / floor.
4. Reverse: focusing or hovering a `FieldRow` that has a `part` highlights that part in 3D.
5. `PartPopover.tsx`: drei `<Html>` near the selected part: part name + 1–2 G1 `NumberInput`s (window %, construction
   thickness) writing through the same store setters; close button; keyboard reachable; doesn't cover the part at 390.
6. Tests: store/selection unit tests; part→section mapping test; FieldRow highlight test (testing-library).
7. `npm test`, `npm run build` (studio) green; frozen guard empty; `frameloop="demand"` kept.
8. Live check (scratch :4103/:5276): click the south window → Openings opens, South window field highlighted and
   visible; click roof → Materials/roof; focus the East window field → east window highlighted. Screenshots 1440 +
   390, light + dark; 0 console errors (THREE.Clock warning allowed).

## Notes from G3 review
Cylinder wall facets carry `orientation` + `azimuthDeg` but no stable `id`; dome facets have ids. Derive the
`PartId` from `orientation` (`wall:<o>` / `window:<o>`); dome band-2 facets → `roof`. Storeys = 2 repeats the wall
ring in a translated group — both storeys map to the same `wall:<o>`/`window:<o>`.

## Rules
Selection must not trigger a preview (it's not a design change). Touch: tap = select (no hover on touch).
No gizmos/drag editing (user decision).

**Gotchas found while writing the verification script (no product bugs — all script-side fixes):**
1. `page.getByLabel('South window', {exact:true})` is ambiguous — the Openings section's `SliderField` renders
   *both* a range `<input>` and a `NumberInput`, both labelled "South window" (one as `role=slider`, one as
   `role=spinbutton`). Fixed by scoping to `getByRole('spinbutton', ...)`.
2. `anchorPosition()`'s wall midpoint (`wall:<o>`) sits at the wall's horizontal *and* vertical center — exactly
   where a centered window hole also sits. Clicking `wall:S` after giving South a real window selects `window:S`
   instead (the glass pane is in front, correctly). Not a bug: a person would see the same thing (there's no wall to
   click through a window). The wall-click check instead uses `wall:E`, which still had WWR 0 (no hole) and, given
   this camera's fixed `[+x,+y,+z]`-ish position, is one of the two camera-facing walls (`wall:N`/`wall:W` are on the
   far side and occlude nothing there — a raycast at their anchor point failed to hit them, again correctly).
3. Re-submitting the *same* percentage into the popover a second time (e.g. 40% again on a second shape) is a true
   no-op in `NumberInput.apply` (`if (next !== value) onChange(...)`) — it correctly does **not** re-fire a preview
   request. The cylinder/2-storey repeats of condition 5 each use a different value (45%, 50%) so the "typed change
   DOES fire preview" assertion stays meaningful.
4. A `fullPage` screenshot at 390 px width is really a fixed-viewport screenshot here, not a stitched full-document
   one — `Studio.tsx`'s own root is a capped `h-[calc(100dvh-56px)] overflow-hidden` (F3's own fix for the viewer's
   camera-framing bug), so the *inner* row scrolls, not the document; whatever that inner div's scroll position was
   at capture time is what the screenshot shows. A `FieldRow`'s `scrollIntoView` on a fresh page load can scroll well
   past the viewer before the popover screenshot — legitimate (proves condition 3's "scrolls into view", captured
   separately) but not what the light/dark/1440/390 popover screenshot set wants alongside the viewer, so those
   shots toggle theme in place (clicking the header's "Light"/"Dark" `Segmented`) instead of a `localStorage` +
   reload, which avoids a fresh remount re-triggering the scroll.
