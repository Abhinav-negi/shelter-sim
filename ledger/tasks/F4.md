# F4 — Landing, auth pages, dashboard, compare
Status: DONE      Depends on: F3, P2

## Goal
The product around the studio: a cinematic but restrained landing page, login/register, "Your shelters", and a
factual comparison view.

## Read
`ledger/PLAN.md` (§Design system, §Client) · `apps/studio-server/API.md` · `apps/studio/src/{viewer,results,api,design}/**`

## May touch / must not touch
May: `apps/studio/src/routes/{Landing,Auth,Dashboard,Compare}*/**`. Must not: the viewer, results internals, server,
frozen. **No npm install.**

## Conditions
1. Landing: a full-bleed live ShelterViewer hero at dawn; "Design for the cold." / "Simulate your shelter before you
   build it." / **Design a shelter →** · *Explore the technology*; 4 stages (Design, Fast physics, Compare,
   High-fidelity validation, which is text only, honest future work). Every chart shown comes from a real preview call.
2. Auth pages: minimal forms with field-level errors from the API.
3. Dashboard: a grid of the user's designs (name, location, updated, last dawn temp if run), "+ New shelter", and an
   empty state "Start your first shelter" with an action. Delete asks for confirmation.
4. Compare: pick 2–4 designs, overlay the indoor curves, and show a KPI table with deltas vs the first. No scores.
5. Checked against PLAN.md's banned list. Screenshots of every page at 1440 and 390 px, light and dark.

## Evidence

**Starting point.** `routes/{Landing,Login,Register}.tsx` already existed as real (not placeholder) F1/F1b
scaffolding — Login/Register already called the real `login`/`register` API wrappers and showed *an* error, just
always under the password field regardless of which field the API blamed. `Dashboard.tsx`/`Compare.tsx` were
explicit placeholders (`/** Placeholder — F4 wires this up ... */`). `App.tsx` already registered all five routes,
so no routing changes were needed.

**Condition 1 (Landing).** Hero: `<section className="relative h-[64vh] min-h-[420px] ... overflow-hidden">` with
an `absolute inset-0` div holding a lazy `<ShelterViewer design={options.defaults} options={options} hour={6} />`
(three stays out of the eager bundle — see bundle-size gotcha below) and a `relative z-10` solid `bg-paper` text
panel anchored bottom-left (no transparency/blur — avoids anything glassmorphism-adjacent). CTA now points at
`/register` (was `/login` in the placeholder; a first-time visitor has no account yet). The 4 stages are an ordered,
single-column, hairline-divided list (`0N` + title + body), not a card/feature grid — matches PLAN.md's "quiet
editorial sequence" and stays clear of the banned generic 3-column grid. Stage 4 ("High-fidelity validation") is
text-only, explicitly "Future work ... Not built yet." Under stage 2 ("Fast physics") a `LivePreviewChart` fires a
real `POST /api/simulate/preview` against `options.defaults` on mount and renders the real `TemperatureChart` on
success; on failure it renders nothing (no fake/placeholder chart — confirmed API.md §4: `/api/simulate/preview`
has no auth requirement, so there is no reason a landing-page call would need faking). Verified live: the chart on
`landing-1440-light-stages.png` is a real indoor/outdoor curve for the Ladakhi-byre-at-Leh default, matching the
Studio page's own chart shape for the same design.

**Condition 2 (auth field-level errors).** `Login.tsx`/`Register.tsx` now track `{field?, message}` from
`ApiError.field`/`ApiError.message` (confirmed server-side: `apps/studio-server/src/app.ts`'s error handler maps an
ajv `instancePath` like `/password` to `field: 'password'`, §"ajv validation error -> ... field name") and route the
message to the matching `FieldRow`'s `error` prop; a field-less error (e.g. `EMAIL_TAKEN`, `INVALID_CREDENTIALS`,
`NETWORK_ERROR`) renders as a plain banner above the submit button instead of being misattributed to the password
field (the placeholder's old behaviour). Register's password field also has a permanent "At least 8 characters."
hint that a real field error temporarily replaces (`FieldRow` only ever shows one of hint/error — existing,
untouched component). Live-verified: submitting Register with a 5-char password (the form has `noValidate`, so the
browser doesn't block it — the request really reaches the server) shows "must NOT have fewer than 8 characters"
under the Password field; submitting Login with a wrong password shows `INVALID_CREDENTIALS`'s message as a
field-less banner, then succeeds once the password is corrected.

**Condition 3 (Dashboard).** `GET /api/designs` (newest-first) renders as a hairline-divided list — not a boxed
card grid, consistent with PLAN.md §Design system ("hairline rules and whitespace, not cards") and with how the
rest of the app (`Kpis.tsx`, `TemperatureChart`'s legend) already presents grouped data — each row showing name
(linked to `/app/design/:id`), resolved location name (preset id → `options.locations` name, or the custom
location's own name), `updated <date>`, and the latest run's dawn temp in °C via `fmtC` (results/format.ts,
imported not copied) or "Not run yet". **N+1, as flagged in the brief**: there is no
"latest-simulation-per-design" batch route, so the dawn temp needs one `GET /api/designs/:id/simulations` per
design (`Promise`-per-row, not awaited sequentially) — acceptable for a single user's own small design list; noted
here rather than adding a server route (out of scope, server is frozen for this task). Empty state ("Start your
first shelter." + a primary "New shelter" button) only renders when the list is empty. Delete is a **two-step
inline confirm** (click "Delete" → row shows "Delete this design? [Delete] [Cancel]"), not `window.confirm()` — the
app already has zero native dialogs, and a styled two-state row fits PLAN.md's "hairline + whitespace" instrument
aesthetic better than a modal would. A "Log out" ghost button (`POST /api/auth/logout` then `navigate('/login')`)
lives here rather than in `components/shell/AppShell.tsx`, which is outside this task's "may touch" list.

**Condition 4 (Compare).** A checkbox picker (`routes/compare` — new dir) lists every saved design; 2–4 selection
enforced (an unchecked box disables itself once 4 are picked); selection syncs to `?ids=` via `useSearchParams`
(shareable link, and F4.md's own `/app/compare?ids=` route shape from PLAN.md §Client). For each selected design:
`GET /api/designs/:id/simulations` (newest first) → its latest id → `GET /api/simulations/:id` for the full
`SimulationFull` (kpis + result), cached per id so re-selecting never re-fetches. A design with no saved run gets a
plain sentence + an "Open in Studio →" link instead of being silently dropped (brief note under "Notes"); the
chart/table render once ≥2 selected designs actually have a run. `routes/compare/OverlayChart.tsx` overlays each
ready design's **indoor** curve only (not outdoor — PLAN.md condition 4 says "overlay the indoor curves"; each
design's own outdoor/location context is already on its Studio page, and up to 4 different outdoor curves for
possibly-different locations would be noise) — first (baseline) design in `var(--ink)`, the rest in the thermal
tokens (`--thermal-hottest/-coldest/-warm`) in order; this reuses the thermal palette, which the design system
reserves for temperature data, and this literally is temperature data across designs, not an unrelated use.
`routes/compare/kpiTable.ts`'s pure `buildKpiTable()` builds the 9-row KPI table (same fields as `results/Kpis.tsx`
— that file has no exported form to import from, being must-not-touch/import-only, so the label list is
necessarily re-declared here, not copied-and-diverged; the *formatting* helper `kToC` from `results/format.ts` **is**
imported) with an explicit `+`/`-` signed delta vs `designs[0]` (never a ranking/score — no colour-coding a
"winner", no sorting by any KPI, just plain numbers and their difference from the first pick). Unit-tested in
`kpiTable.test.ts` (4 tests: row order/labels, Kelvin→°C conversion + delta arithmetic, explicit negative-delta
sign, 3-design support).

**Condition 5 (banned list + screenshots).** Checked against PLAN.md's banned list explicitly: no glassmorphism, no
gradient blobs (the landing hero's sky is the pre-existing, frozen `ShelterViewer`'s own physical fog/sky
rendering, not a decorative CSS gradient), no purple/blue gradients, no pill badges, no heavy shadows, no fake
stats/logos/testimonials, no stock imagery, no icon confetti, no generic 3/4-column feature grid (the 4 stages are
a single-column numbered list), no decorative motion. 24 screenshots (Landing/Login/Register/Dashboard-empty/
Dashboard-filled/Compare × 1440×900 + 390×844 × light + dark) — all read by eye; **one real bug found and fixed**:
the Compare KPI `<table>` had a hard-coded `min-w-[420px]`, wider than the 390 px viewport, clipping the right
design's column off-screen with no scroll affordance visible in the static view (`overflow-x-auto` made it
technically scrollable but visually looked broken/cut). Fixed by removing the arbitrary min-width and letting the
table size to its own content — at 390 px with 2 designs (the common case) it now fits with no scrolling needed at
all, even in the worst-case where both designs share the longest name ("Untitled shelter") in the header row;
`overflow-x-auto` stays as a graceful fallback for a legitimate 3-4-column case that doesn't fit. Re-screenshotted
(`compare-390-fullpage.png`) to confirm all 9 KPI rows are readable with no clipping. Everything else — landing
hero/stages, login/register forms + field errors, dashboard empty/filled/long-name/delete-confirm, compare picker
empty/2-selected states — was clean on first look at both widths/themes.

**Bundle-size gotcha (not a stated condition, but breaks the "lazy so landing text renders immediately" intent).**
First build put the eager `index-*.js` chunk at 662 kB because `Landing.tsx` imported `TemperatureChart` (pulls in
`recharts`) directly, and `Compare.tsx` imported `OverlayChart` (same) directly — `Studio.tsx`'s own precedent
(`ResultsPanel` is `lazy()`ed specifically so recharts doesn't load with Login/Landing, per its own comment) wasn't
being followed. Fixed by `lazy()`-wrapping `TemperatureChart` in `Landing.tsx` and `OverlayChart` in `Compare.tsx`,
each behind its own `<Suspense>`. Final build: eager `index-*.js` 303 kB (vs. F2's baseline "~271 kB
landing/login chunk" — the modest increase is Dashboard/Compare's own new code, not recharts), `LineChart-*.js`
350 kB (recharts core, now genuinely lazy, shared by `TemperatureChart`/`OverlayChart`/`ResultsPanel`),
`ShelterViewer-*.js` 959 kB (three, unchanged, already lazy from F2).
