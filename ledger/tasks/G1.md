# G1 — Typed numeric entry
Status: TODO      Depends on: –      Phase: Studio v2 (`ledger/V2.md` §G1)

## Goal
Every numeric control in the Studio controls panel can be typed from the keyboard (e.g. type `10` into the South
window % instead of dragging), while the slider stays. Includes the orientation dial (azimuth).

## Conditions
1. `SliderField`'s value readout (`SliderField.tsx:45`) is a `NumberInput`: `type="number"`, `inputMode="decimal"`,
   mono, unit suffix shown, accessible label = the field label. Slider and input stay in sync both ways.
2. Keeps a local draft string; commits on Enter and on blur; clamps to `[min,max]`; rounds to `step` (and to
   `decimals` for display); Escape reverts the draft; invalid/empty text reverts without calling onChange; native
   ↑/↓ step works.
3. `OrientationDial` gets the same input for azimuth (−180..180 °).
4. All 7 numeric controls (length, width, height, 3 × thickness, 4 × window %) work through it with no per-caller
   changes beyond what's needed (window % is already in % units: `OpeningsSection` passes ×100).
5. New `SliderField.test.tsx` (testing-library): type `10`+Enter → onChange(10); `999`+Enter → onChange(max);
   `abc` → no onChange, input shows old value; Escape → reverts; blur commits.
6. `npm test -w @shelter/studio` all green (73 before + new), `npm run build -w @shelter/studio` clean, frozen guard empty.
7. Screenshots 1440 + 390, light + dark, of the Studio controls panel showing the inputs; 0 console errors.

## Rules
Units in mono. No layout shift when typing. The input is compact (≈ the old readout's `w-20`). No new dependency.

## Evidence

**Decisions**
- New `apps/studio/src/components/ui/NumberInput.tsx`: a controlled `<input type="number" inputMode="decimal">`
  wrapped in a `w-20` span with a unit `<span>`, matching the old readout's footprint exactly (no layout shift).
  Keeps a local `draft` string (`useState`) plus an `editing` ref. The input's own `onChange` only updates
  `draft` (so partial/invalid typing never calls the caller's `onChange`); `commit()` (called on Enter and on
  blur) parses, and on empty/`NaN` reverts the draft to the current formatted `value` without calling `onChange`
  — otherwise clamps to `[min,max]`, rounds to `step` (`Math.round(v/step)*step`), reformats to `decimals`, and
  calls `onChange` only if the result differs from the current value. Escape resets `draft` to the current
  value's formatted string, no commit. A `useEffect` resyncs `draft` from `value` whenever it changes externally
  (e.g. slider drag) *unless* `editing.current` is true, so mid-typing edits aren't clobbered by a sibling
  slider's `onChange` round-trip.
- `label` prop is *always* applied as `aria-label` on the input (not relying on an external `<label htmlFor>`),
  so it works standalone in `OrientationDial.tsx` (no `FieldRow` there) as well as inside `SliderField.tsx`
  (which also has a `FieldRow` label — redundant but harmless; `aria-label` wins as the accessible name either
  way, and both point at the same text so there's no mismatch).
- `SliderField.tsx`: replaced the `<span>{value.toFixed(decimals)}{unit}</span>` readout with `<NumberInput
  value onChange min max step={step ?? 1} decimals unit label={label} disabled />`. Deliberately did **not**
  pass an explicit `id` — `SliderField`'s own `useId()` is already used for the `<Slider>` (`id={id}`) and the
  `FieldRow`'s `htmlFor`; giving `NumberInput` the same `id` would have produced two elements sharing one DOM id.
  `NumberInput` falls back to its own internal `useId()` when no `id` prop is passed, and doesn't need one since
  it self-labels via `aria-label`.
- `OrientationDial.tsx`: replaced the plain `<p>{Math.round(value)}°</p>` readout with `<NumberInput value
  onChange min max step unit="°" label="Orientation" />` (decimals left at the default 0, matching the old
  `Math.round` display). No other changes to the dial's pointer/keyboard logic.
- Native ↑/↓ spinner/arrow-key stepping on the number input updates the visible `draft` immediately (it's a
  normal `onChange` event) but, like manual typing, does **not** push to the caller's `onChange` until
  Enter/blur — consistent with condition 2's "commits on Enter and on blur" (auto-committing every keystroke,
  including a native step, would call `onChange` with intermediate/partial values, which conditions 2 and 5
  explicitly rule out). Not covered by an automated test (condition 5 only lists the four typed scenarios +
  blur); confirmed by reading the DOM events, not exercised live.

**Gotchas for a cold successor**
- **jsdom + `<input type="number">` coerces invalid text to `""`.** `fireEvent.change(input, {target:{value:
  'abc'}})` does *not* leave `input.value === 'abc'` in jsdom (matching real browser behavior for numeric
  inputs) — it becomes `""`. So the "abc" test case and the "empty" case are actually the same code path
  (`draft.trim() === ''`) in this component; both revert without calling `onChange`. Verified this is real jsdom
  behavior (not a bug in the component) by inspecting the failing/passing assertions directly.
- **RTL doesn't auto-`cleanup()` between tests here.** `vitest.config.ts` does not set `test.globals: true`, so
  `@testing-library/react`'s automatic `afterEach(cleanup)` registration (which only fires when it detects a
  global `afterEach`) never runs. `Segmented.test.tsx` has only one `it()` so this was invisible before. My new
  `SliderField.test.tsx` has 5, and without an explicit `afterEach(cleanup)` import every test's `render()`
  output piled up in the same `document.body`, so `getByRole(...)` matched the same field from a *previous*
  test's un-unmounted tree too ("Found multiple elements..."). Fixed by importing `cleanup` from
  `@testing-library/react` and calling `afterEach(cleanup)` at the top of the new test file. Left
  `Segmented.test.tsx` untouched (out of scope, still passes as-is); a future test file with >1 `it()` will hit
  the same trap unless it does the same.
- **Distinguishing the slider vs. the number input in RTL queries**: both now share the same accessible name
  (the field label), so `getByLabelText(label)` is ambiguous. Used `getByRole('slider', {name})` for the
  `<input type=range>` and `getByRole('spinbutton', {name})` for the `<input type=number>` — reliable, no
  extra `data-testid` needed.
- **Headless theme switching for screenshots**: the `Segmented` control renders each option as a `<label>`
  wrapping a `sr-only` (visually hidden) `<input type=radio>`; a Playwright click on `getByRole('radio', {name})`
  times out because the hidden input has zero visible area and the label element itself intercepts the pointer
  event. Clicking the label's own text (`getByRole('radiogroup', {name:'Theme'}).getByText('Light'|'Dark',
  {exact:true})`) works reliably.
- **Independently-scrolling `<aside>` panel**: clicking/filling the South-window field mid-panel scrolled that
  `<aside>` (its own `overflow-y-auto`, not the document) to bring the focused field into view, which then
  pushed Geometry/Orientation out of frame for later screenshots. Reset via `document.querySelectorAll('aside')
  .forEach(el => el.scrollTop = 0)` before each shot (plus `document.scrollingElement.scrollTop = 0` for the
  mobile/390 layout, where the row is normal document flow instead).
