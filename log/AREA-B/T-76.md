**Why this exists.** T-70 gave `simulate()` a way to accept a warm start
(`SimOptions.initialTemperatureK`), but no way to hand one back out. T-54 wired T-70's hook into
`@shelter/optimise`'s spin-up-sharing cache and measured the honest result: a **uniform** warm
start (the only thing available from outside the engine — `SimulationResult` exposes only named
per-channel series, never the raw solved node vector) gives a real but small ~1.08–1.20x speedup,
not the required 2x, because it corrects only the overall temperature *level*, not the *spatial
gradient* through each wall's thickness. T-70's own Evidence block (test 3) already proved the
gradient is what actually matters: seeding with the real converged per-node profile, merely offset
+20 K uniformly (right shape, wrong level), converged in 4 days vs cold's 7 — a 1.75x day-count
reduction from shape alone, on top of whatever the level correction buys. `integrate()` already
computes this exact per-node vector internally (`RunOutput.finalT`,
`packages/engine/src/solve/integrator.ts`) — it is thrown away at the end of every `simulate()`
call today (`index.ts` destructures `records, initialT, warnings, spinUpDaysUsed` from `integrate()`
but never `finalT`). This task's entire job is to stop throwing it away, and hand it back
**opaquely** — a caller must store it and pass it straight back via
`options.initialTemperatureK`, never inspect or reorder it, because the engine's internal node
order is deliberately not part of the public contract (CONTRACTS.md §7.7) and may change.

**This task does NOT wire the new field into `@shelter/optimise`.** That continuation belongs to
T-54 (a different task, a different file allow-list) once this field exists and is proven here in
isolation — exactly the same split T-70 used.
